## 一、A3：回收站 ZIP 导出

### 1.1 目标

- 管理员可把回收站按模块导出为 ZIP；
- 覆盖：客户 / 人员 / 文件 / 任务 / 激励 / 提醒；
- ZIP 不加密；包含数据清单、校验和、文件内容清单；
- 下载链接 7 天过期；
- 导出/下载/删除全部审计；
- 恢复时回到原客户（文件、任务、激励、提醒按原 `customer_id`/`owner_id` 恢复）；
- 非 admin 403；跨租户不可见。

### 1.2 数据模型（新表）

```sql
CREATE TABLE biz_recycle_export (
  id BIGINT PRIMARY KEY AUTO_INCREMENT,
  tenant_id BIGINT NOT NULL DEFAULT 1,
  export_no VARCHAR(40) NOT NULL,
  requested_by BIGINT NOT NULL,
  types_json JSON NOT NULL COMMENT '["customer","user","file","task","incentive","reminder"]',
  filter_json JSON NULL COMMENT 'deleted_at 范围/关键字/组织',
  status VARCHAR(20) NOT NULL DEFAULT 'pending' COMMENT 'pending/running/ready/failed/expired',
  file_path VARCHAR(500) NULL,
  file_size BIGINT NULL,
  checksum_sha256 CHAR(64) NULL,
  expires_at DATETIME NOT NULL,
  downloaded_at DATETIME NULL,
  error_msg VARCHAR(500) NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  UNIQUE KEY uk_recycle_export_no (tenant_id, export_no),
  KEY idx_recycle_export_expire (status, expires_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

文件落 NAS 导出目录（与上传目录隔离）：`{export_dir}/{tenant}/{export_no}.zip`；仓库只存路径，不存字节。

### 1.3 权限与审计

- 新功能码建议：`system:recycle:export`，加入 `ADMIN_ONLY`；admin 角色绑定。
- 端点：
  - `POST /api/system/recycle/exports`（创建，body: types/filter）
  - `GET /api/system/recycle/exports`（列表，admin）
  - `GET /api/system/recycle/exports/{id}/download`（下载，admin + 未过期）
  - `DELETE /api/system/recycle/exports/{id}`（删除，admin）
- 每次创建/下载/删除写 `SecurityAuditService.permissionChange("recycle_export_*", ...)` 和 `sys_log`。

### 1.4 ZIP 结构

```text
export-<export_no>/
  manifest.json          # 导出时间、类型、条数、过滤条件、版本
  checksums.sha256       # 每个文件 SHA-256
  data/
    customers.csv
    users.csv
    files.csv
    tasks.csv
    incentives.csv
    reminders.csv
  files/
    <fileId>/<safeFileName>   # 仅 deleted=1 且内容仍存在的文件
```

- CSV UTF-8 BOM（Excel 中文兼容），列含 `id/tenant_id/deleted_at/deleted_by/reason` 与业务关键字段；
- 文件内容按 `biz_file.oss_key` 读取；内容已物理清除的只写清单行，写 `contentMissing=true`；
- 不导出密码哈希、JWT、密钥、session、审计内部字段；人员只导出必要字段（username/realName/dept/status/leave）。
- 路径安全：`sanitizeZipEntryName` 复用文件模块规则，防 `../`。

### 1.5 导出流程

1. 校验 admin + types 白名单 + filter 范围；
2. 生成 `export_no`，插入 `pending`；
3. 异步任务（`@Async`/线程池）分批读：
   - 每类每次 500 行，写 CSV / 文件流；
   - 大文件复制到 ZIP 时流式写入，不整包进堆；
   - 单次导出上限（建议 10 万行/类型，文件总量 20GB；
     超限拒绝并提示缩小范围）；
4. 写 manifest + checksums；计算 ZIP SHA-256；
5. 更新 `ready`，`expires_at=now+7d`；
6. 定时任务扫描 `ready && expires_at<now` → 删 ZIP，置 `expired`。

### 1.6 过期与清理

- 下载接口：`expires_at < now` → 410 Gone；
- 定时任务每小时清理过期 ZIP（软状态 `expired` + 物理删除）；
- 管理员手动删除同样物理删除；
- 7 天从“生成完成”起算，不因下载续期。

### 1.7 恢复原客户

- 导出不改变恢复逻辑：现有 `RecycleService.restore*` 已按原 `customer_id/owner_id/folder_id` 恢复；
- 导出只在 `manifest.json` 记录 `restoreHint`：
  - 文件：`originalCustomerId`（从 `biz_file_link`/激励记录反查；无则 null）
  - 任务/激励/提醒：`customerId`
  - 客户/人员：原 `owner/dept/office`
- 恢复时仍走现有闸门：同名活跃客户、原负责人已删、公海残留、内容已清除；
- 若原客户已删除，提示先恢复客户，不自动挂到新客户。

### 1.8 测试计划

**单测/集成**

1. admin 创建导出 → 202/200，状态 pending→ready；
2. 非 admin 创建/列表/下载 → 403；
3. 过期下载 → 410；清理任务置 expired 并删文件；
4. ZIP 内 manifest/checksums 行数一致；checksum 校验通过；
5. 文件名 `../x` 被清洗；
6. 空类型/非法类型 → 400；
7. 客户/人员/文件/任务/激励/提醒各 1 条被导出（字段抽查）；
8. 内容已清除文件：清单有行、`contentMissing=true`、无文件条目；
9. 审计日志有 create/download/delete 三条。

**运行时（测试服）**

- 临时 admin/非 admin；造 6 类各 1 条回收站数据；
- 导出→下载→解压校验；7 天过期用 SQL 改 `expires_at` 模拟 → 410；
- 非 admin 403；审计查询命中。

### 1.9 风险/取舍

- 大 ZIP 长时间占用连接：异步生成，下载走流式；
- 文件字节可能很大：不打包“未删除”的文件，只打包回收站；超限拒绝；
- 不加密是用户拍板；导出包含个人信息，必须 admin-only + 7 天 + 审计；
- 导出任务多实例：任务表加锁/状态机，防重复生成；建议 `SELECT ... FOR UPDATE SKIP LOCKED`（MySQL 8）。

## 二、A4：交接/组织移动审批人=销售总监（配置化）

### 2.1 目标

- 默认审批人 = 销售总监角色（`role_code` 由管理员在审批配置中选择，**不硬编码角色 ID/人员**）；
- 管理员可更换角色/人员；
- 在途单审批人快照：创建时写 `approver_id`，后续角色成员变化不改变在途单；
- 审批人离职/停用：管理员可转交，写审计；不自动静默换人。

### 2.2 数据与配置

复用：

- `biz_approval_config(flow_type, approver_type, approver_ids, sign_mode, status)`；
- `biz_lifecycle_request.approver_id`（已有快照）。

新增建议：

```sql
ALTER TABLE biz_lifecycle_request
  ADD COLUMN approver_snapshot_json JSON NULL COMMENT '创建时审批人快照: type/id/name/source',
  ADD COLUMN approver_changed_by BIGINT NULL,
  ADD COLUMN approver_changed_at DATETIME NULL,
  ADD COLUMN approver_change_reason VARCHAR(255) NULL;
```

`approver_snapshot_json` 例：

```json
{"type":"ROLE","roleCode":"sales_director","roleId":9,"userId":17,"userName":"…","resolvedAt":"…"}
```

### 2.3 审批人解析

创建交接/组织移动时：

1. 读 `biz_approval_config` 的 `handover`/`org_move` 最新启用配置；
2. `approver_type=ROLE`：`approver_ids` 为角色 ID 列表；取该角色下**第一个启用且未删除**的用户；
3. `approver_type=USER`：直接取用户（管理员可指定个人）；
4. `approver_type=DEPT`：取部门负责人/首个启用用户（保留扩展）；
5. 无可用审批人 → 400 “未配置审批人/角色下无可用人员”；
6. 写 `approver_id` + `approver_snapshot_json`。

**不硬编码**：SQL 只按 `role_code`/配置 ID 查，不在代码写销售总监角色 ID 或姓名。
生产销售总监 `role_code` 为 `0`（角色 ID 因环境而异，不能写死）；审批配置由管理员选择角色，文档示例以“生产实际 role_code”为准。

**本稿决策（需复检确认）**：接受“角色下第一个启用成员审批 + 管理员转交”的单人快照模型。
若业务要求“角色内任一启用成员都可批”，需增加 `approver_role_id` 快照并改审批校验，作为 A4 的后续变更，不在本稿默认范围。

### 2.4 在途单规则

| 场景 | 行为 |
|---|---|
| 创建后角色成员变化 | 在途单 `approver_id` 不变（快照） |
| 原审批人停用/删除 | 不能审批；管理员在“交接/调动申请”页点“转交审批人” |
| 管理员转交 | `POST /requests/{id}/transfer-approver`，body `newApproverId/reason`；仅 pending；写 `approver_changed_*` + 审计；通知新审批人 |
| 审批人自己申请 | 仍拒绝“审批人不能是申请人”（现有） |
| 配置被删/停用 | 在途单仍按快照；新建单报“未配置审批人” |

### 2.5 端点/UI

- 审批配置页：`handover`/`org_move` 选择“指定角色”（已支持 ROLE），提示“默认选销售总监角色；角色下第一个启用人员审批”。
- 申请列表：显示 `approver_name` + 快照来源；admin 显示“转交审批人”按钮。
- 转交接口权限：`system:user:edit` + admin 或当前审批人；服务层校验 pending。

### 2.6 测试

1. 配置 `handover` ROLE=销售总监 → 创建单 `approver_id` = 该角色第一个启用用户；
2. 角色新增/删除成员 → 在途单审批人不变；
3. 原审批人停用 → 审批 403；admin 转交 → 新审批人 200；
4. 非 admin 转交 → 403；
5. 无配置/角色无人员 → 400，提示明确；
6. `org_move` 同套；
7. 审批人=申请人 → 400 拦截；
8. 审计：创建/转交/审批都有记录。

### 2.7 迁移/初始化

- 不预置角色 ID；上线时由管理员在“审批配置”新增两条流程：
  - `handover` → 审批人类型=角色 → 销售总监（生产 role_code=0，以实际为准）；
  - `org_move` → 同上。
- 若希望脚本初始化，按生产 `role_code='0'`（销售总监，实际以管理员确认为准）查 ID 插入，不写死数字；执行前需管理员确认角色码。
