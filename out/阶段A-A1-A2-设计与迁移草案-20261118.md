## 一、A1：授权继承递归 + 组织子树

### 1.1 现状与缺口

当前 `biz_file_grant`：

- `object_type=FOLDER` 只匹配“文件直属 folder_id”，**不递归子文件夹**；
- `scope_org_id` 只做 `==` 精确匹配，**不覆盖组织子树**；
- `DENY` 优先、管理员豁免已实现；
- 文件/文件夹的归属组织快照是 `biz_file.org_id` / `biz_file_folder.org_id`（上传/建夹时写死，随组织移动改派）。

目标：

1. 对父文件夹的 FOLDER 授权，`inherit=1` 时可覆盖子文件夹及其文件；
2. `scope_org_id` 指向大区/办事处/部门时，覆盖其所有下级组织节点；
3. DENY 仍优先于 ALLOW、上传者本人、组织矩阵；管理员仍豁免；
4. 列表行级 `perms`、单文件下载、文件夹操作三处同口径。

### 1.2 判定模型

#### A1-1 文件夹祖先链

新增内部方法（`FileGrantService`）：

```text
folderAncestors(folderId) -> Set<Long>
  - 从 folderId 开始，沿 biz_file_folder.parent_id 向上，最多 50 层；
  - 包含自身；
  - 遇到 null/0/已删除/环立即停止（防脏数据死循环）。
```

判定：

- `coversFile(g, file)`：
  - `g.object_type=FOLDER` 且 `g.inherit=1` 且 `g.object_id ∈ folderAncestors(file.folder_id)` → 命中；
  - `inherit=0` 只对文件夹自身操作生效，不对文件生效；
- `coversFolder(g, folder)`：
  - `g.object_id == folder.id` → 命中（不限 inherit）；
  - `g.object_id ∈ folderAncestors(folder.id)` 的祖先且 `inherit=1` → 命中；
- 无夹文件（folder_id null）不吃 FOLDER 授权，仍只吃 SPACE/FILE 授权。

#### A1-2 组织子树

复用现有 `sys_org_closure(ancestor_id, descendant_id, depth)`：

```text
orgAncestors(targetOrgId) -> Set<Long>
  - SELECT ancestor_id FROM sys_org_closure WHERE descendant_id=?;
  - 加上 targetOrgId 自身；
  - 闭包表不可用 → 退化精确匹配（fail-closed，不放大）。
```

判定：

- `g.scope_org_id == null` → 不限组织；
- 否则按 `scope_mode` 判定：
  - `SUBTREE`（新配置默认）：`g.scope_org_id ∈ orgAncestors(target.org_id)`；
  - `EXACT`（A2 迁移旧行默认）：`g.scope_org_id == target.org_id`；
- 语义：`SUBTREE` 授权写在大区 X，覆盖 X 及下属办事处/部门；写在办事处 Y，只覆盖 Y 及下属部门；不会向上覆盖 X 的兄弟节点。

#### A1-3 优先级

```text
admin → 豁免（不看 DENY）
DENY（任意命中）→ 拒绝
ALLOW（任意命中）→ 放行
ABSTAIN → 回落旧 biz_folder_type_default / 组织矩阵 / 本人/上级链
```

保持现有 `FileGrantService.Decision` 三态不变；`FolderPermissionService.checkFile/check`、`FileService.canAccessFile/canDownloadFile` 已接入的点不变。

### 1.3 性能设计

| 场景 | 查询 |
|---|---|
| 单文件下载/判定 | 1 次 grant 查询 + 1 次 `sys_org_closure` 查询 + 最多 5 次文件夹父链点查（可缓存） |
| 列表 `permsForFiles` | 建议新增 `decideFiles(List<BizFile>, action, userId)`：一次预载全部 folder 行 + 一次闭包查询，内存展开，避免 N×层查询 |
| 文件夹树 | 一次预载 `biz_file_folder`，内存构建 parent 索引 |

实现建议：

- `FileGrantService` 增加可选依赖 `JdbcTemplate`、`BizFileFolderMapper`（`@Autowired(required=false)`，保持现有单测构造器不变）；
- `FolderPermissionService.permsForFiles` 已有 `refCache`（folderId→folder），扩展为“祖先集合缓存”；
- `orgAncestors` 在一次 `decideFiles` 调用内按 orgId 记忆化，不跨请求缓存（组织移动后立即生效）。

### 1.4 迁移与兼容

A1 **不需要改表**：`sys_org_closure`、`biz_file_folder.parent_id` 已存在。建议只加索引（草案见 `docs/design/phase-a/V2026.11.18.1__file_grant_inheritance_indexes.sql.draft`）：

```sql
ALTER TABLE biz_file_grant
  ADD KEY idx_file_grant_scope_org (tenant_id, scope_org_id);
```

兼容：

- `inherit=0` 语义不变（只对夹自身）；
- 旧 `biz_folder_type_default` 继续走旧判定链；
- `scope_org_id` 精确匹配的行仍命中（闭包包含自身）；
- 组织闭包缺失时退化为精确匹配，不放大权限。

### 1.5 测试计划

**单测（`FileGrantServiceTest` 扩展 / 新 `FileGrantInheritanceTest`）**

1. 父夹 A → 子夹 B → 文件 F：A 上 `FOLDER view ALLOW inherit=1` → F `ALLOW`；
2. 同上 `inherit=0` → `ABSTAIN`；
3. 父夹 A 上 `DENY view`，子夹 B 文件 F（非 admin owner）→ `DENY`；
4. 兄弟夹 C 文件不受 A 授权影响；
5. `scope_org_id=大区X`，文件 `org=部门Z`（Z 是 X 后代）→ `ALLOW`；
6. `scope_org_id=办事处Y`，文件 `org=Z`（Z 是 Y 后代）→ `ALLOW`；
7. `scope_org_id=无关部门` → `ABSTAIN`；
8. 闭包表为空/异常 → 退精确匹配；
9. admin 在 DENY 下仍放行（既有规则）。

**运行时（测试服，临时数据）**

1. 建 A/B 两级夹 + B 内文件，非 owner 用户；
2. A 上 `ALLOW view inherit=1` → 列表可见 + 下载 200；
3. 改 `inherit=0` → 下载 403、行 perms 无 view；
4. A 上 `DENY view` → owner 下载 403（非 admin）；
5. 组织树：大区 X → 办事处 Y → 部门 Z，文件 `org=Z`；
6. `scope_org_id=X` → 200；`scope_org_id=Y` → 200；无关节点 → 403；
7. 删除/重建闭包后同结果；记录 SQL、HTTP 码、行 perms。

### 1.6 风险

- 递归继承会让“父夹 ALLOW”比现状更宽；迁移前需给管理员一份“受影响授权清单”（父夹授权数、子夹/文件数）。
- `scope_org_id` 子树会让“大区授权”覆盖下属办事处/部门；需在权限中心 UI 明示“含下级组织”。
- 文件夹父链有环/孤儿时 fail-closed（到断点停止），不抛 500。
- 列表性能：必须做批量预载；否则 100 行 × 5 层会放大。

## 二、A2：`biz_file_grant` 主链切换

### 2.1 目标与原则

- 把 `biz_folder_type_default`（下称“旧表”）存量授权迁移到 `biz_file_grant`（下称“新表”）；
- 读路径：新引擎为主，旧表只读兜底 + 开关；
- **不删旧表**，保留回滚；
- 对账 0 差异后再切；
- 存量行为不变（ALLOW/过期/组织范围/主体类型）。

### 2.2 字段映射

| 旧表 | 新表 | 规则 |
|---|---|---|
| `tenant_id` | `tenant_id` | 原样 |
| `subject_type` ROLE/USER | 同 | 原样；如未来 POSITION 再扩 |
| `subject_id` | 同 | 原样 |
| `object_type` FILE + `folder_id IS NULL` | `SPACE` | `object_id=NULL`，`scope_level=folder_type` |
| `object_type` FILE + `folder_id` | `FOLDER` | `object_id=folder_id`，`inherit=1` |
| `object_type` FOLDER + `folder_id IS NULL` | `SPACE` | `object_id=NULL`，`scope_level=folder_type`，动作通常 create |
| `object_type` FOLDER + `folder_id` | `FOLDER` | `object_id=folder_id`，`inherit=1` |
| `perms` CSV | 每动作一行 | `FIND_IN_SET` 展开；`edit`→`edit`；`rename/replace`→`edit` 去重；`create`→`create` |
| `scope_org_id` | 同 | 原样（新引擎按子树解释；旧表历史语义精确匹配，需在切换前评估是否放宽） |
| `scope_level` | 同 | 原样 |
| `expires_at` | `expire_at` | 原样；NULL=永久 |
| `created_by/created_at` | 同 | 原样 |
| 无 | `effect` | `ALLOW` |
| 无 | `inherit` | SPACE=0；FOLDER=1 |
| 无 | `legacy_ref` | `ftd:<旧id>:<动作>` 唯一 |
| 无 | `source` | `legacy` |

> 注意：旧表 `scope_org_id` 历史是精确匹配；A1 新引擎改为子树后，历史“大区授权”会变宽。A2 切换前必须输出“将被放宽的旧行”清单，由管理员确认；未确认可先把这些行迁成 `scope_org_id` 精确语义（增加新列 `scope_mode=EXACT/SUBTREE`），默认 `SUBTREE`。草案 SQL 先按 `SUBTREE` 写，评审时定。

### 2.3 新表结构增补（草案）

```sql
ALTER TABLE biz_file_grant
  ADD COLUMN legacy_ref VARCHAR(120) NULL COMMENT '旧表迁移来源 ftd:<id>:<action>',
  ADD COLUMN source VARCHAR(20) NOT NULL DEFAULT 'manual' COMMENT 'manual/legacy/migration',
  ADD COLUMN scope_mode VARCHAR(10) NOT NULL DEFAULT 'SUBTREE' COMMENT 'SUBTREE/EXACT（兼容旧精确语义）',
  ADD UNIQUE KEY uk_file_grant_legacy (tenant_id, legacy_ref),
  ADD KEY idx_file_grant_scope_org (tenant_id, scope_org_id);
```

### 2.4 迁移步骤（分四步，可回滚）

1. **DDL**：加 `legacy_ref/source/scope_mode` 与索引（草案 `.2`）。
2. **数据迁移**：按 §2.2 插入新表；`NOT EXISTS legacy_ref` 幂等；不删旧表。
3. **对账**：只读脚本比对旧表与新表 `legacy_ref` 行：
   - 旧行数 vs 新迁移行数；
   - 每 `(tenant, subject, object, action)` 缺失/多余；
   - 过期时间、scope_org_id/scope_level、effect；
   - 输出 CSV；有差异则退出非 0，禁止切换。
4. **切换**：
   - 配置 `file.grant.mode=legacy|dual|new`（默认 `legacy`）；
   - 先 `dual`：新引擎命中 ALLOW/DENY 即生效，ABSTAIN 回落旧表；
   - 观察 1 个发布周期 + 对账 0 差异 → `new`（ABSTAIN 不再回落旧表）；
   - 回滚：改回 `legacy`，旧表未动。

### 2.5 旧配置入口双写

旧表仍由“文件权限”页保存。切换期必须双写，否则管理员新配置只进旧表、新引擎看不到：

- `FolderTypeDefaultService.saveGrant/delete/renew` 内新增 `LegacyFileGrantSyncService`：
  - 保存/续期：按 §2.2 映射 `upsert` 新表（`legacy_ref` 为空，`source=dual_write`）；
  - 删除：删除对应 `source=dual_write` 行；
  - 事务：旧表与新表同事务（同一数据源）；
  - 失败：回滚整个保存，不允许“旧表成功/新表失败”。
- `file.grant.mode=legacy` 时双写仍执行（为将来切换积累数据）；`new` 后旧入口可改为只写新表（下一阶段）。

### 2.6 读路径改造

`FolderPermissionService` 当前结构是“新引擎例外层 → 旧判定链”。A2 改为显式模式：

```text
mode=legacy: 跳过 FileGrantService，完全旧链
mode=dual:   FileGrantService 先判；ALLOW/DENY 返回；ABSTAIN → 旧链
mode=new:    FileGrantService 先判；ALLOW/DENY 返回；ABSTAIN → 拒绝（不再旧链）
```

- `check/checkFile/permsForFiles/permsForBatch` 四处统一；
- 旧表读取只作为 `dual` 的 fallback；
- `file.grant.mode` 用配置中心，不重启生效优先（若实现成本高，先环境变量 + 重启）。

### 2.7 对账与测试

**对账脚本（草案 `reconcile-file-grants.sql`，只读）**

- 输出：
  - `missing_in_new`：旧表有、新表 `legacy_ref` 无；
  - `extra_in_new`：新表 `source=legacy` 但旧表无；
  - `field_diff`：expire/scope/level/effect 不一致；
  - `counts`：旧行、新迁移行、按动作分布。
- 退出码：有差异 ≠ 0。

**单元/契约测试**

1. 旧表一行 `public ROLE 06 view,upload,share,download` → 新表 4 行 SPACE、`scope_level=public`；
2. 旧表 `FILE + folder_id=10` → 新表 FOLDER#10、inherit=1；
3. 旧表 `FOLDER + folder_id=10 create` → 新表 FOLDER#10 action=create；
4. `expires_at` 空 → 新表 null；有值 → 原值；
5. 旧表 `rename/replace` 不重复生成 action；
6. 重跑迁移幂等（`legacy_ref` 唯一，行数不变）；
7. `mode=dual` 下旧行为不变（用现有文件权限测试全量回归）；
8. `mode=new` 下旧表有、新表无的授权 → 拒绝（用测试库断言行）。

**运行时**

- 测试库备份 → 迁移 → 对账 0 → `dual`：
  - 抽样 3 个角色 × public/private/incentive × view/download/edit/delete，比较迁移前后 `GET /api/file/list` 行 perms 与下载状态码；
  - 逐夹授权（7 行 ACL）抽样；
  - DENY/ALLOW/继承/过期/组织子树各 1 例；
- 回滚：切 `legacy`，行为恢复到迁移前。

### 2.8 迁移前冲突清单

```sql
-- 只读：同一主体+对象+动作出现多个 scope 的旧行
SELECT subject_type, subject_id, object_type,
       CASE WHEN folder_id IS NULL THEN 'SPACE' ELSE 'FOLDER' END AS new_object_type,
       folder_id, action, COUNT(*) AS rows_cnt,
       GROUP_CONCAT(CONCAT(scope_level, '/', COALESCE(scope_org_id,'NULL')) ORDER BY id) AS scopes
  FROM ( /* 同 .2 的动作展开 */ ) x
 GROUP BY subject_type, subject_id, object_type, folder_id, action
HAVING COUNT(*) > 1;
```

处置顺序：

1. 若 scope 相同 → 合并（取永久/最晚过期）；
2. 若 scope 不同 → 先由管理员确认“最宽 scope”，迁移脚本按确认结果只写一行；
3. 未确认的冲突行不迁移，列入 `manual_review`，切 `new` 前必须清零。

### 2.9 风险与回滚

| 风险 | 处置 |
|---|---|
| 旧表 `scope_org_id` 精确→子树变宽 | `scope_mode=EXACT` 兼容列 + 切换前“放宽清单”人工确认 |
| 旧表 `edit` 伞拆动作后语义差异 | 统一映射为 `edit`，由 `actionsFor` 覆盖 manage |
| 旧表重复行/同动作多 scope | 新表 `uk_file_grant` 不含 scope，同主体+对象+动作只能一行；迁移前必须按“最宽 scope”去重并输出冲突清单，否则插入失败或静默丢范围 |
| 旧表重复行 | `legacy_ref` 唯一 + 迁移 `NOT EXISTS`；对账报告重复 |
| 双写失败 | 同事务回滚；监控告警 |
| 切换后新表漏行 | `dual` 阶段 ABSTAIN 仍回落旧表；对账 0 才 `new` |
| 回滚 | `file.grant.mode=legacy`；旧表未删；新表可保留 |

## 三、交付顺序（A1/A2 实现阶段）

1. A1 代码 + 单测 + 运行时（不改表，仅索引草案）。
2. A2 DDL + 迁移脚本 + 对账脚本（先在测试库副本演练）。
3. A2 双写 + 模式开关 + 旧行为全量回归。
4. 对账 0 → 测试服 `dual` → 观察 → `new`；生产仍不动。
5. 每步提交 + 测试 + 证据，交独立复检。
