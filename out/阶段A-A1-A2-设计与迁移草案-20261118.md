## 一、A1：授权继承递归 + 组织子树

### 1.1 现状与缺口

当前 `biz_file_grant`：

- `object_type=FOLDER` 只匹配“文件直属 folder_id”，**不递归子文件夹**；
- `scope_org_id` 只做 `==` 精确匹配，**不覆盖组织子树**；
- `DENY` 优先、管理员豁免已实现；
- 文件/文件夹的归属组织快照是 `biz_file.org_id` / `biz_file_folder.org_id`（上传/建夹时写死，随组织移动改派）。

目标：

1. 对父文件夹的 FOLDER 授权，`inherit=1` 时可覆盖子文件夹及其文件；
2. `scope_org_id` 指向大区/办事处/部门时，覆盖其所有下级组织节点；
3. DENY 仍优先于 ALLOW、上传者本人、组织矩阵；管理员仍豁免；
4. 列表行级 `perms`、单文件下载、文件夹操作三处同口径。

### 1.2 判定模型

#### A1-1 文件夹祖先链

新增内部方法（`FileGrantService`）：

```text
folderAncestors(folderId) -> Set<Long>
  - 从 folderId 开始，沿 biz_file_folder.parent_id 向上，最多 50 层；
  - 包含自身；
  - 遇到 null/0/已删除/环立即停止（防脏数据死循环）。
```

判定：

- `coversFile(g, file)`：
  - `g.object_type=FOLDER` 且 `g.inherit=1` 且 `g.object_id ∈ folderAncestors(file.folder_id)` → 命中；
  - `inherit=0` 只对文件夹自身操作生效，不对文件生效；
- `coversFolder(g, folder)`：
  - `g.object_id == folder.id` → 命中（不限 inherit）；
  - `g.object_id ∈ folderAncestors(folder.id)` 的祖先且 `inherit=1` → 命中；
- 无夹文件（folder_id null）不吃 FOLDER 授权，仍只吃 SPACE/FILE 授权；
- 根夹 `parent_id=0`/null 视为祖先链终点，不把 0 当组织/文件夹 ID；
- 父链遇 `deleted=1` 或检测到环立即停止（fail-closed）。

#### A1-2 数据范围：ANY / RELATIVE / EXACT / SUBTREE

旧表 `scope_level` 是**相对当前查看人**的数据范围（self/dept/office/region/all），旧引擎还忽略 `scope_org_id`；
新引擎不能用绝对的 `scope_org_id` 直接替代。新表必须区分：

- `space_type`：SPACE 的空间类型（public/private/incentive/fabushi），不再复用 `scope_level`；
  代码 `coversFile/coversFolder` 的 SPACE 匹配必须改为 `g.space_type == file.fileScope`；
  旧 `scope_level` 只作数据范围，不得再参与空间类型匹配；
- `scope_mode`：
  - `ANY`：不限（旧 NULL/all）；
  - `RELATIVE`：保留旧 `scope_level`，按当前查看人用 `ScopeResolver` 判定；
  - `EXACT`：绝对组织精确匹配；
  - `SUBTREE`：绝对组织子树匹配（新手工授权默认）。

`RELATIVE` 判定（与旧 `scopeCovers` 同口径）：

```text
scope_level = null/all       -> 放行（ANY 等价）
scope_level = self           -> target.uploader/owner == 当前用户
scope_level = dept/office/region
  target.org_id != null      -> resolveDeptScope(currentUser, level).contains(target.org_id)
  target.org_id == null      -> resolveScope(currentUser, level).contains(target.uploader)
```

复用现有 `sys_org_closure(ancestor_id, descendant_id, depth)` 只用于 `SUBTREE`：

```text
orgAncestors(targetOrgId) -> Set<Long>
  - SELECT ancestor_id FROM sys_org_closure WHERE descendant_id=?;
  - 加上 targetOrgId 自身；
  - 闭包表不可用 → 退化精确匹配（fail-closed，不放大）。
```

判定：

- `scope_mode=ANY` → 不限；
- `scope_mode=RELATIVE` → 按上方旧 `scopeCovers` 口径（需注入 `OrgScopeResolver`，按当前查看人解析）；
- `scope_mode=SUBTREE` → `g.scope_org_id ∈ orgAncestors(target.org_id)`；
- `scope_mode=EXACT` → `g.scope_org_id == target.org_id`；
- 语义：`SUBTREE` 授权写在大区 X，覆盖 X 及下属办事处/部门；写在办事处 Y，只覆盖 Y 及下属部门；不会向上覆盖 X 的兄弟节点。

#### A1-3 优先级

```text
admin → 豁免（不看 DENY）
DENY（任意命中）→ 拒绝
ALLOW（任意命中）→ 放行
ABSTAIN → 回落旧 biz_folder_type_default / 组织矩阵 / 本人/上级链
```

保持现有 `FileGrantService.Decision` 三态不变；`FolderPermissionService.checkFile/check`、`FileService.canAccessFile/canDownloadFile` 已接入的点不变。

### 1.3 性能设计

| 场景 | 查询 |
|---|---|
| 单文件下载/判定 | 1 次 grant 查询 + 1 次 `sys_org_closure` 查询 + 最多 5 次文件夹父链点查（可缓存） |
| 列表 `permsForFiles` | 建议新增 `decideFiles(List<BizFile>, action, userId)`：一次预载全部 folder 行 + 一次闭包查询，内存展开，避免 N×层查询 |
| 文件夹树 | 一次预载 `biz_file_folder`，内存构建 parent 索引 |

实现建议：

- `FileGrantService` 增加可选依赖 `JdbcTemplate`、`BizFileFolderMapper`（`@Autowired(required=false)`，保持现有单测构造器不变）；
- `FolderPermissionService.permsForFiles` 已有 `refCache`（folderId→folder），扩展为“祖先集合缓存”；
- `orgAncestors` 在一次 `decideFiles` 调用内按 orgId 记忆化，不跨请求缓存（组织移动后立即生效）。

### 1.4 迁移与兼容

A1 **不需要改表**：`sys_org_closure`、`biz_file_folder.parent_id` 已存在。建议只加索引（草案见 `docs/design/phase-a/V2026.11.18.1__file_grant_inheritance_indexes.sql.draft`）：

```sql
ALTER TABLE biz_file_grant
  ADD KEY idx_file_grant_scope_org (tenant_id, scope_org_id);
```

兼容：

- `inherit=0` 语义不变（只对夹自身）；
- 旧 `biz_folder_type_default` 继续走旧判定链；
- `scope_org_id` 精确匹配的行仍命中（闭包包含自身）；
- 组织闭包缺失时退化为精确匹配，不放大权限。

### 1.5 测试计划

**单测（`FileGrantServiceTest` 扩展 / 新 `FileGrantInheritanceTest`）**

1. 父夹 A → 子夹 B → 文件 F：A 上 `FOLDER view ALLOW inherit=1` → F `ALLOW`；
2. 同上 `inherit=0` → `ABSTAIN`；
3. 父夹 A 上 `DENY view`，子夹 B 文件 F（非 admin owner）→ `DENY`；
4. 兄弟夹 C 文件不受 A 授权影响；
5. `scope_org_id=大区X`，文件 `org=部门Z`（Z 是 X 后代）→ `ALLOW`；
6. `scope_org_id=办事处Y`，文件 `org=Z`（Z 是 Y 后代）→ `ALLOW`；
7. `scope_org_id=无关部门` → `ABSTAIN`；
8. 闭包表为空/异常 → 退精确匹配；
9. `RELATIVE`：旧 scope_level=self/dept/office/region 分别按当前查看人判定；
10. 部门新增/改父后重建 `sys_org_closure`，子树授权立即生效（不缓存组织树）；
11. admin 在 DENY 下仍放行（既有规则）。

**运行时（测试服，临时数据）**

1. 建 A/B 两级夹 + B 内文件，非 owner 用户；
2. A 上 `ALLOW view inherit=1` → 列表可见 + 下载 200；
3. 改 `inherit=0` → 下载 403、行 perms 无 view；
4. A 上 `DENY view` → owner 下载 403（非 admin）；
5. 组织树：大区 X → 办事处 Y → 部门 Z，文件 `org=Z`；
6. `scope_org_id=X` → 200；`scope_org_id=Y` → 200；无关节点 → 403；
7. 父夹 ALLOW/DENY 对子夹文件、兄弟夹隔离各 1 例；
8. 部门新增/改父后重建闭包，子树授权立即生效；
9. 删除/重建闭包后同结果；记录 SQL、HTTP 码、行 perms。

### 1.6 风险

- 递归继承会让“父夹 ALLOW”比现状更宽；迁移前需给管理员一份“受影响授权清单”（父夹授权数、子夹/文件数）。
- `scope_org_id` 子树会让“大区授权”覆盖下属办事处/部门；需在权限中心 UI 明示“含下级组织”。
- 文件夹父链有环/孤儿时 fail-closed（到断点停止），不抛 500。
- 列表性能：必须做批量预载；否则 100 行 × 5 层会放大。

## 二、A2：`biz_file_grant` 主链切换

### 2.1 目标与原则

- 把 `biz_folder_type_default`（下称“旧表”）存量授权迁移到 `biz_file_grant`（下称“新表”）；
- 读路径：新引擎为主，旧表只读兜底 + 开关；
- **不删旧表**，保留回滚；
- 对账 0 差异后再切；
- 存量行为不变（ALLOW/过期/组织范围/主体类型）。

### 2.2 字段映射

| 旧表 | 新表 | 规则 |
|---|---|---|
| `tenant_id` | `tenant_id` | 原样 |
| `subject_type` ROLE/USER | 同 | 原样；如未来 POSITION 再扩 |
| `subject_id` | 同 | 原样 |
| `object_type` FILE + `folder_id IS NULL` | `SPACE` | `object_id=NULL`；**`space_type=folder_type`**（不是 `scope_level`）；`space_type=NULL` 表示任意空间（兼容旧 blank，见 §2.10） |
| `object_type` FILE + `folder_id` | `FOLDER` | `object_id=folder_id`，`inherit=1` |
| `object_type` FOLDER + `folder_id IS NULL` | `SPACE` | `object_id=NULL`；`space_type=folder_type`，动作通常 create |
| `object_type` FOLDER + `folder_id` | `FOLDER` | `object_id=folder_id`，`inherit=1` |
| `perms` CSV | 每动作一行 | `FIND_IN_SET` 展开；`edit`→`edit`；`rename/replace`→`edit` 去重；`create`→`create` |
| `scope_level` NULL/空/all | `scope_mode=ANY` | `scope_level=NULL`，`scope_org_id=NULL`（旧语义不限） |
| `scope_level` self/dept/office/region | `scope_mode=RELATIVE` | **保留旧 level**；按当前查看人 `ScopeResolver` 判定 |
| 旧 `scope_org_id` | `scope_org_id=NULL` | 旧引擎忽略该列；不得当成绝对组织迁移 |
| `expires_at` | `expire_at` | 原样；NULL=永久 |
| `created_by/created_at` | 同 | 原样 |
| 无 | `effect` | `ALLOW` |
| 无 | `inherit` | SPACE=0；FOLDER=1 |
| 无 | `legacy_ref` | `ftd:<旧id>:<动作>` 唯一 |
| 无 | `source` | `legacy` |

> 旧表 `scope_level` 是“相对当前查看人”的数据范围，**不是空间类型**；`folder_type` 才是 public/private/incentive。
> 旧 `scope_org_id` 生产/测试实际全为 NULL，迁移不得假设存在绝对组织。
> 新手工授权默认 `scope_mode=SUBTREE`；旧行迁移按 `ANY/RELATIVE`。

### 2.3 新表结构增补（草案）

```sql
ALTER TABLE biz_file_grant
  DROP INDEX uk_file_grant,
  ADD COLUMN space_type VARCHAR(20) NULL COMMENT 'SPACE 空间类型 public/private/incentive/fabushi',
  ADD COLUMN legacy_ref VARCHAR(120) NULL COMMENT '旧表迁移来源 ftd:<id>:<action>',
  ADD COLUMN source VARCHAR(20) NOT NULL DEFAULT 'manual' COMMENT 'manual/legacy/dual_write/migration',
  ADD COLUMN scope_mode VARCHAR(10) NOT NULL DEFAULT 'SUBTREE' COMMENT 'ANY/RELATIVE/EXACT/SUBTREE',
  ADD COLUMN object_key BIGINT AS (COALESCE(object_id,0)) STORED,
  ADD COLUMN scope_key VARCHAR(200) AS (
    CONCAT_WS('|', COALESCE(space_type,''), COALESCE(scope_mode,''),
              COALESCE(scope_level,''), COALESCE(scope_org_id,0))
  ) STORED,
  ADD UNIQUE KEY uk_file_grant_scope
    (tenant_id, subject_type, subject_id, object_type, object_key, action, scope_key),
  ADD UNIQUE KEY uk_file_grant_legacy (tenant_id, legacy_ref),
  ADD KEY idx_file_grant_scope_org (tenant_id, scope_org_id);
```

> 新唯一键包含 `space_type + scope_mode + scope_level + scope_org_id`，保留多 scope 行；
> 不再使用“同主体+对象+动作只能一行”的旧 `uk_file_grant`。

### 2.4 迁移步骤（分四步，可回滚）

1. **DDL**：加 `space_type/legacy_ref/source/scope_mode/scope_key` 与新唯一键（草案 `.1`）。
2. **数据迁移**：按 §2.2 插入新表；`NOT EXISTS legacy_ref` 幂等；不删旧表。
3. **对账**：只读脚本比对旧表与新表 `legacy_ref` 行：
   - 旧行数 vs 新迁移行数；
   - 每 `(tenant, subject, object, action)` 缺失/多余；
   - 过期时间、space_type/scope_mode/scope_level/scope_org_id、effect；
   - 输出 CSV；有差异则退出非 0，禁止切换。
4. **切换**：
   - 配置 `file.grant.mode=legacy|dual|new`（默认 `legacy`）；
   - 先 `dual`：新引擎命中 ALLOW/DENY 即生效，ABSTAIN 回落旧表；
   - 观察 1 个发布周期 + 对账 0 差异 → `new`（ABSTAIN 不再回落旧表）；
   - 回滚：改回 `legacy`，旧表未动。

### 2.5 旧配置入口双写

旧表仍由“文件权限”页保存。切换期必须双写，否则管理员新配置只进旧表、新引擎看不到：

- `FolderTypeDefaultService.saveGrant/delete/renew` 内新增 `LegacyFileGrantSyncService`：
  - 保存/续期：按 §2.2 映射 **upsert** 新表；`legacy_ref='ftd:<旧id>:<action>'` 与迁移行同键；
  - 若 `legacy_ref` 已存在（迁移/上一次双写）→ **按唯一键更新原行**，保留既有 `source`（`legacy`/`dual_write`），不新插；
  - 若不存在 → 插入 `source='dual_write'`；
  - **create/rename/replace 必须纳入映射**：`create` 保留，`rename/replace` 归并 `edit`；不得 400 或静默丢弃；
  - 同一旧配置改动后，动作集合变化：删除该 `ftd:<oldId>:` 下已不存在的动作行，再 upsert 新动作；
  - 删除：删除该 `ftd:<oldId>:` 下全部 `legacy/dual_write` 行；
  - 事务：旧表与新表同事务（同一数据源）；
  - 失败：回滚整个保存，不允许“旧表成功/新表失败”；
  - reconcile：读取 `source IN ('legacy','dual_write')`，双写行按同一 `legacy_ref` 与旧表比较；
  - 单测：改配置后 `legacy_ref` 不被改成新行、对账仍 0；删除旧行后新表对应 `ftd:<id>:` 全清；含 create/rename/replace；失败注入旧表回滚。
- `file.grant.mode=legacy` 时双写仍执行（为将来切换积累数据）；`new` 后旧入口可改为只写新表（下一阶段）。

### 2.6 API/UI/契约同步（A2 实施前必做）

当前 `FileGrantDialog.vue`、`FileGrantController.FileGrantRequest`、`FileGrantService.Command` 仍把空间类型放在 `scopeLevel`；切 `space_type` 后必须全链路同步：

1. `Command`/`FileGrantRequest` 增加 `spaceType`；
2. `SPACE` 时 `spaceType` 必填，校验 `public|private|incentive|fabushi`；
3. UI 表单“空间”下拉绑定 `form.spaceType`；列表列显示 `spaceType`；
4. `FileGrantService.coversFile/coversFolder` 的 SPACE 分支改为 `space_type` 匹配；
5. `docs/api/api-list.md/json` 重生成；权限页/契约（action gate、endpoint parity）回归；
6. 补保存/读取/匹配测试：POST SPACE 带 spaceType → GET 返回 → 文件/夹匹配。

### 2.7 space_type NULL 语义

- 旧表 `folder_type` 为空/blank 的 SPACE 行迁移后 `space_type=NULL`；
- 新引擎定义：`space_type=NULL` = **任意空间**（兼容旧 blank，避免旧授权失效）；
- 非 NULL 必须是 `public/private/incentive/fabushi` 之一；
- 新 UI 保存 SPACE 时禁止空值（必填）；
- 单测：space_type=NULL 的 SPACE 授权对 public/private 文件均命中；非法值保存 400。

### 2.8 读路径改造

`FolderPermissionService` 当前结构是“新引擎例外层 → 旧判定链”。A2 改为显式模式：

```text
mode=legacy: 跳过 FileGrantService，完全旧链
mode=dual:   FileGrantService 先判；ALLOW/DENY 返回；ABSTAIN → 旧链
mode=new:    FileGrantService 先判；ALLOW/DENY 返回；ABSTAIN → 跳过旧表
             （注意：只跳过 biz_folder_type_default；owner/manager/公共矩阵/私人空间规则仍继续）
```

- `mode=new` **不是**“无 grant 即拒绝”：owner/manager 恒管、公共夹按 data_scope、私人空间仅本人/上级链等基础规则必须继续生效；只是不再回落到旧 `biz_folder_type_default`。
- `check/checkFile/permsForFiles/permsForBatch` 四处统一；
- 旧表读取只作为 `dual` 的 fallback；
- `file.grant.mode` 用配置中心，不重启生效优先（若实现成本高，先环境变量 + 重启）。

### 2.9 对账与测试

**对账脚本（草案 `reconcile-file-grants.sql`，只读）**

- 输出：
  - `missing_in_new`：旧表有、新表 `legacy_ref` 无；
  - `extra_in_new`：新表 `source=legacy` 但旧表无；
  - `field_diff`：expire/scope/level/effect 不一致；
  - `counts`：旧行、新迁移行、按动作分布。
- 退出码：有差异 ≠ 0。

**行为对账（行对账 0 ≠ 语义不变）**

固定 3 个测试角色（销售员/行政/销售总监）× 3 个空间（public/private/incentive）× 4 个动作（view/download/edit/delete）：

1. 迁移前用旧引擎记录：列表行 `perms`、单文件下载/操作 HTTP 状态码；
2. 迁移后 `mode=legacy` 应完全一致；
3. 切 `mode=dual` 再记录一次；逐项 diff，必须 0；
4. 额外固定夹具：owner 无 grant、公共夹 data_scope、private 他人、过期 grant、scope_level=self/region、逐夹授权；
5. 输出 `behavior-before.json/after-dual.json` 与 diff；有差异禁止切 `new`。

**单元/契约测试**

1. 旧表一行 `public ROLE 06 view,upload,share,download` → 新表 4 行 SPACE、`space_type=public`、`scope_mode=ANY`；
2. 旧表 `scope_level=region` → 新表 `scope_mode=RELATIVE`、`scope_level=region`、`scope_org_id=NULL`；
3. 旧表 `scope_org_id=5`（旧引擎忽略）→ 新表仍 `scope_org_id=NULL`；
4. 旧表 `FILE + folder_id=10` → 新表 FOLDER#10、inherit=1；
5. 旧表 `FOLDER + folder_id=10 create` → 新表 FOLDER#10 action=create；
6. `expires_at` 空 → 新表 null；有值 → 原值；混合组 → 永久；
7. 旧表 `rename/replace` 归并 `edit` 不重复；
8. 重跑迁移幂等（`legacy_ref` 唯一，行数不变）；
9. 同一主体+对象+动作、不同 scope → 新表保留多行（唯一键含 scope_key）；
10. `mode=dual` 下旧行为不变（现有文件权限测试全量回归）；
11. `mode=new` 下旧表有、新表无的授权不再回落；但 owner/公共/私人基础规则仍按原链：
    - owner 无显式 grant 下载 200；
    - 公共夹按 data_scope 200/403；
    - private 他人 403。

**运行时**

- 测试库备份 → 迁移 → 对账 0 → `dual`：
  - 抽样 3 个角色 × public/private/incentive × view/download/edit/delete，比较迁移前后 `GET /api/file/list` 行 perms 与下载状态码；
  - 逐夹授权（7 行 ACL）抽样；
  - DENY/ALLOW/继承/过期/组织子树各 1 例；
- 回滚：切 `legacy`，行为恢复到迁移前。

### 2.10 迁移前冲突清单

```sql
-- 只读：同一主体+对象+动作出现多个 scope 的旧行
SELECT subject_type, subject_id, object_type,
       CASE WHEN folder_id IS NULL THEN 'SPACE' ELSE 'FOLDER' END AS new_object_type,
       folder_id, action, COUNT(*) AS rows_cnt,
       GROUP_CONCAT(CONCAT(scope_level, '/', COALESCE(scope_org_id,'NULL')) ORDER BY id) AS scopes
  FROM ( /* 同 .2 的动作展开 */ ) x
 GROUP BY subject_type, subject_id, object_type, folder_id, action
HAVING COUNT(*) > 1;
```

处置顺序（2026-11-18 评审后修正）：

1. 新唯一键 `uk_file_grant_scope` 已包含 `space_type/scope_mode/scope_level/scope_org_id`，**不同 scope 的行允许并存**；
2. 同一完整 scope 的重复动作 → 合并（取永久/最晚过期），不丢范围；
3. 仍然输出该清单作为审计证据；不再要求人工“取最宽 scope”。

### 2.11 风险与回滚

| 风险 | 处置 |
|---|---|
| 新表存量手工授权 `scope_org_id` 语义 | `.1` 回填：有 scope_org_id 的存量行 `scope_mode=EXACT`，保持现状；新手工授权默认 SUBTREE |
| 旧表 `edit` 伞拆动作后语义差异 | 统一映射为 `edit`，由 `actionsFor` 覆盖 manage |
| 旧表同动作多 scope | 新唯一键含 scope_key，允许并存；同完整 scope 的重复动作合并并输出清单 |
| 旧表重复行 | `legacy_ref` 唯一 + 迁移 `NOT EXISTS`；对账报告重复 |
| 双写失败 | 同事务回滚；监控告警 |
| 切换后新表漏行 | `dual` 阶段 ABSTAIN 仍回落旧表；对账 0 才 `new` |
| 回滚 | `file.grant.mode=legacy`；旧表未删；新表可保留 |
