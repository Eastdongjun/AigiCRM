## 三、阶段 2：权限与数据范围收口

### 3.1 法布施文件组织数据范围

新增真实消费轴：

- `fabushi|file_view`：按上传人（OWNER 锚）判定，默认 `all`（公司级）；管理员可在权限中心按角色/人员收窄到大区/办事处/部门/self。
- `fabushi|file_delete`：独立功能码 + 数据范围；默认 admin `all`，其他角色 `self`（未授权功能码时无实际效果）。
- `file|version_rollback`：文件版本回滚独立功能码 + 数据范围；默认 admin `all`，其他角色 `self`。

实现点：

- `FolderPermissionService.fabushiVisibleUploaderIds/canViewFabushiFile/canDeleteFabushiFile/canRollbackVersion`
- `FileService.pageFiles` 对 `scope=fabushi` 按可见上传人过滤；跳过普通文件夹树逻辑（法布施无文件夹）
- `FileService.deleteFile` 法布施分支改为“功能码 + 数据范围”双门
- `FileService.canDownloadFile` 法布施下载与列表同口径（不再仅 `fabushi:view` 裸放行）
- `PermissionMetadataService.SCOPE_AXIS`、`RolePermScopeService.CONSUMED_AXIS`、`check-scope-axis-contract.sh` 三处同步
- 迁移 `V2026.11.17.2__fabushi_version_rollback_org_scope.sql`

### 3.2 `biz_file_grant` 统一授权引擎

新增 `BizFileGrant` / `BizFileGrantMapper` / `FileGrantService`：

- 按 USER / ROLE / POSITION 主体匹配
- 对象：SPACE / FOLDER / FILE；FOLDER 支持 `inherit`
- `DENY` 优先于 `ALLOW`，也优先于“上传者本人恒管”；管理员不受 DENY 影响
- `expire_at` 过期即忽略；`scope_org_id` 精确匹配组织快照
- 未命中返回 `ABSTAIN`，调用方继续旧 `biz_folder_type_default` 判定，存量行为不变
- 已接入 `FolderPermissionService.check/checkFile/permsForFiles/permsForBatch` 与法布施/版本回滚判定

> 这是“统一授权引擎”的运行时接入，不是全量替换：旧类型默认授权仍是主链，新表是例外层。管理端已有 `/api/file/grants` CRUD 与“文件权限 → 统一授权”弹窗（`file:acl:manage` 门禁）。

### 3.3 前端

- `FileTable.vue` 版本历史回滚按钮支持 `file:version:rollback`（保留 `file:edit` 兼容）
- 法布施行删除按钮继续按 `fabushi:file:delete`，行级 `perms` 由后端同码点亮
- 权限生成物 PC/MP 同步（94 码）
- 新增 `LifecycleDialog.vue`（离职交接/组织调动/审批记录），挂在人员管理页头，动作按钮按 `system:user:edit` / `approval:view` 门禁

## 四、阶段 3：生命周期、回收站、上传与预览

### 4.1 离职交接 / 组织移动

新增：

- 表：`biz_lifecycle_request`、`biz_lifecycle_item`（迁移 `V2026.11.17.3`）
- 服务：`LifecycleService`；控制器：`LifecycleController`
- 审批人来源：`biz_approval_config` 的 `handover` / `org_move` 流程；**不硬编码人员**
- 审批配置页新增两个流程类型；支持指定人员/角色，一级审批（复用现有配置页）
- 交接迁移当前数据：客户、任务、待办提醒、文件、文件夹、在办审批/待办节点；可选复制角色（默认关闭）
- 组织移动（人员跨部门）：更新 `sys_user.dept_id/office_id/org_id`、当前客户 `dept_id/office_id`、当前文件/文件夹 `org_id`
- 每条受影响行写 `biz_lifecycle_item`，回滚按请求精确恢复；历史/已删除行不动
- 权限：创建/回滚 `system:user:edit`；审批/驳回 `system:user:edit` 或 `approval:view`，服务层再校验“配置的审批人或管理员”

### 4.2 任务/激励统一回收站

- `BizTask` 补 `deletedAt/deletedBy/deletedReason`；新 `DELETE /api/task/{id}` 软删
- `BizIncentiveRecord` 补 `@TableLogic deleted` 与审计字段；`deleteRecord` 改为软删
- `RecycleService` 新增：`/api/system/recycle/tasks`、`/tasks/{id}/restore`、`/tasks/{id}/purge`；`/incentives` 同组
- `RecycleBinService` 统一写 `biz_recycle_bin`：客户/人员/文件/任务/激励/提醒删除写快照，恢复/彻底删除回写 `restored/purged`
- 提醒新增 `deleted/deleted_at/deleted_by/deleted_reason`；`DELETE /api/reminder/{id}` 软删，回收站 `/api/system/recycle/reminders` 可恢复/彻底删除
- 客户/人员/文件原有回收站继续读主表，不改变原页面口径

### 4.3 200MB 分片上传 / 秒传 / 扫描

- 表 `biz_upload_session`；`FileChunkUploadService`：init（5MB/片）→ 逐片可重传 → complete 合并
- complete 复用 `FileService.upload`，因此 scope/文件夹权限/配额/审计不另起一套
- md5 命中同人同 scope/文件夹 → `instant=true`，不重复扣配额
- 单文件上限统一为 **200MB**（`application.yml` 同步 200MB）
- 前端 `UploadDialog.vue`：>10MB 自动走分片，200MB 以上直接拒绝
- `FileScanService`：EICAR 基线永远执行；配置 `file.scan.enabled/command` 后接外部扫描器，失败 fail-closed；上传/替换落盘后、台账前扫描

### 4.4 视频 5 秒预览

- `GET /api/file/{id}/preview`；权限与下载同源 `canDownloadFile`
- ffmpeg 截取 0-5 秒、转 1280 宽 mp4、缓存到缩略图缓存目录
- 仅视频扩展名；非视频 415，ffmpeg 不可用 503，不泄露原文件
- `Dockerfile` 增加 `ffmpeg` 安装（镜像需重建后生效）

## 八、残余缺口（必须知晓，不能当已完成）

1. **交接/组织移动没有默认审批人**：`biz_approval_config` 必须先由管理员新增 `handover` / `org_move` 流程并指定审批人；否则提交返回“未配置审批人”。这是有意的“不硬编码人员”，但上线前必须配置。
2. **组织移动是“人员跨部门”**，不是“部门子树整体移动”；已覆盖 user/客户/文件/文件夹/提醒 `office_id`。任务/激励/审批/财务表没有统一组织快照，未做自动改派；如业务要求需单独定义字段与规则。
3. **交接默认只迁当前工作数据**：客户/任务/提醒/文件/文件夹/在办审批；`transfer_incentives`/`transfer_reports` 已提供可选迁移（默认关闭，需交接单勾选），历史学分与历史业绩默认不随人走。
4. **回收站导出 ZIP 未实现**：`biz_recycle_bin` 已存快照，导出/清理批次/保留期策略仍待做。
5. **视频预览测试镜像未验证**：测试容器镜像无 ffmpeg，端点返回 503；Dockerfile 已补 ffmpeg，需重建镜像后复测。
6. **外部病毒扫描默认关闭**：EICAR 基线已启用；生产需配置 `file.scan.enabled=true` 与 `file.scan.command`（如 clamdscan）并验证。
7. **分片临时目录默认 JVM tmp**：多实例/重启续传需配置 `file.chunk-dir` 到共享 NAS。
8. **法布施数据范围运行时只验证了 all 档**：收窄到大区/办事处/部门/self 的配置链路由单测覆盖，未在测试库做多角色切换实测。
9. **`biz_file_grant` 尚未替换旧 `biz_folder_type_default` 主链**：当前是“旧类型默认 + 新例外层”灰度双读；全量迁移/停旧表未做。
10. **授权继承/组织范围语义有限**：FOLDER 继承只覆盖直属文件，不递归子文件夹；`scopeOrgId` 精确匹配，不支持组织子树（P2，已披露）。
11. **生产未执行**：迁移顺序仍为 ① 迁移 → ② `backfill-customer-name-norm.py` → ③ 应用；生产数据清理/组织移动/交接需单独授权。

## 九、生产上线顺序（建议）

1. 备份生产库 + 上传目录；记录 jar md5。
2. 执行迁移 `.1 → .2 → .3 → .4 → .5 → .6 → .7`。
3. 执行 `scripts/backfill-customer-name-norm.py`（NFKC 回填；SQL 不能替代）。
4. 重建后端镜像（含 ffmpeg），部署新 jar；前端/小程序发布。
5. 管理员在审批配置中新增 `handover` / `org_move` 一级审批人。
6. 灰度验证：法布施列表/删除、版本回滚、分片上传、EICAR、交接/调动各 1 单。
7. 再执行生产数据清理（290 客户/40 人员）与历史数据处置；单独授权。

## 十、结论

本轮把阶段 2 的“法布施/版本回滚组织数据范围 + 统一文件授权引擎”和阶段 3 的“离职交接/组织移动 + 任务/激励回收站 + 200MB 分片/秒传 + 病毒扫描 + 视频预览”做成了可运行、可回滚、可测试的代码，并在测试服做了真实运行验证后完整还原。

**因此：阶段 1-3 核心链路可用、安全；但 §八 各项收口前，不要把本报告理解为“全量生产完成”。**
