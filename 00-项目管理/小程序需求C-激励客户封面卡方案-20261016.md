# 需求 C：激励页客户封面卡 + 客户激励详情页（2026-10-16）

> 独立需求，可单独拍板/排期/上线。定位是**信息架构升级**（列表页瘦身 + 明细下沉到详情页），比需求 B（纯减法）走得更远；不依赖 B，落地后覆盖 B 的目标。
> 来源：产品侧提议"每个客户做成一个封面，点进去再看这个客户的激励详情"。

## 1. 思路

现在客户维度列表把所有明细（分类汇总、照片墙、历史记录、操作按钮）全部平铺在每张卡里，一卡近一屏。改为业界通用的 master-detail：

- **列表页**：每客户一张紧凑封面卡，只留识别信息 + 关键数字
- **详情页**（新增）：该客户的全部激励明细与操作都在这里展开

## 2. 列表页：客户封面卡

```
┌────────────────────────────────┐
│ ┌────┐ 江苏XX医院          128分│
│ │封面│ 医疗 · 安装前    6记录·9文件│
│ │首图 │ ● 未读               NEW │
│ └────┘                          │
└────────────────────────────────┘
```

- 封面 = 该客户最新一张图片缩略（数据已有）；无图 = 分类色渐变 + 客户名首字
- 卡上保留：客户名 / 行业 / 最新大类 / 总积分 / 记录数·文件数 / 未读点 / NEW
- 整卡点击 → 客户激励详情页
- 10 个客户从滚约 10 屏 → 约 2 屏

## 3. 详情页：pages/incentive/customer-detail（新增）

```
┌────────────────────────────────┐
│ ‹ 返回   江苏XX医院       128分  │
│ 医疗 · 进入即自动清除未读        │
│ [安装前 1] [安装中 4] [安装后 1] │ ← 原红圈①变成锚点筛选chips(点击过滤)
├────────────────────────────────┤
│ ▾ 安装前 · 1                    │ ← 分组标题(原②角标职责)
│ [照片墙·纯缩略图,点图即预览]     │ ← 无按钮(原③)
│ ▾ 安装中 · 4 …                  │
├────────────────────────────────┤
│ 历史记录(默认展开)               │
│ · 09-28 安装中留痕 4分  已读      │
│ · 09-12 安装前佐证 2分  已读  ⋯  │ ← 单条操作收进行尾⋯(详情/追加/删除)
├────────────────────────────────┤
│ 吸底栏：［＋ 追加激励］［客户档案］│ ← 原④收敛为2个
└────────────────────────────────┘
```

- 进入详情页即触发已读上报（沿用现有逻辑），说明文案删除
- 「删除最新」从卡底移到对应记录条目的 ⋯ 菜单（删的是记录不是客户）
- 下载能力：预览打开后系统自带保存/转发；条目 ⋯ 菜单里保留显式下载

## 4. 数据与改动范围

**零后端改动**：`getCustomerRecords` 返回的已是按客户聚合结构（customerId / customerName / totalScore / records[] / isNew / unread 全有），详情页经 eventChannel 接收整卡数据即可；返回列表时复用现有 loadRecords 刷新已读态。

改动：新增 customer-detail 页面四件套（app.json 注册）+ `pages/incentive/index.wxml` 客户维度区重写 + index.js 视图函数调整。

**约 2~2.5 人天。零后端、零 DB、PC 不动。**

## 5. 待拍板

1. 封面无图时的样式：分类色渐变+首字（推荐）vs 统一默认底图
2. 卡上"安装前"最新大类是否保留（也可只留未读态）
3. 详情页历史记录默认展开还是折叠（建议默认展开，进详情页就是要看明细）
4. PC 端激励查询页是否连动（建议不动，PC 是表格+画廊结构）
