## 三、缺陷清单（逐条带文件+行号+证据）

### D-01【High】行政角色可见「权限体系/权限管理」Tab，但页内数据接口 403

**现象**：以行政账号 NM100 进入 系统设置 → **权限管理** Tab，页面加载角色的接口立即 403，矩阵页只渲染出外壳（模块导航与说明文字仍在），**角色列缺失且界面不给任何错误提示**。

**实测证据**（`out_NM100.json` + 2026-09-20 复检定向复现）：
```
GET /api/system/roles        -> 403
GET /api/system/menus/tree   -> 403
```
复检精确化（NH100 逐个 Tab 点击）：
- `权限体系` Tab：**无 403**（该 Tab 为静态说明文案，"系统包含5种权限…"）；
- `权限管理` Tab：**403 ×2**，页面仍渲染 `按角色 按岗位 按用户 刷新 权限模块 …` 外壳 → 空矩阵无提示。

即：`权限体系` Tab 上的「前往配置 →」按钮会切到 `权限管理` Tab，从而间接触发同一组 403（解释了首轮扫描把 403 记在「前往配置」名下的原因）。

**权限事实**（`/api/auth/info` 实测）：
```
NM100(行政) system 段 = ['system:config:view','system:dept:view','system:user:add','system:user:edit','system:user:view']
含 system:role:view = False   ← getRoleList 需要
含 system:menu:view = False   ← getMenuTree 需要
含 system:config:view = True  ← 因此能进系统设置页
```

**根因**（前端缺 tab 级门控）：
- `02-迭代源代码/aigicrm-ui/src/views/system/config.vue:32-35`（权限体系 Tab）与 `:36-39`（权限管理 Tab）**没有权限判断**；
- 对照同文件 `:20` 的公海配置 Tab 有正确写法：`v-if="userStore.hasPermission('sea:config:view')"`。

**影响**：属"有入口没权限"——与上一轮已修的两处菜单断链（孤儿菜单 9061、缺父分组 34）同类，但方向相反（有入口无数据）。且失败是**静默**的：`usePermissionData.js:124-125` 用 `catch { permLoadError.value = true }` 置位错误标记，但行政界面上看不到任何提示，管理员会误以为"矩阵本来就是空的"。

**建议**：给这两个 Tab 补 `v-if="userStore.hasPermission('system:role:view')"`（或按设计给行政补绑定），二者取其一，不要两处并存；同时把 `permLoadError` 真正呈现出来。

### D-02【High】积分写接口空请求体返回 500（应为 400）

**现象**：销售总监 NO001 在 积分录入 页点击「保存」「添加行」，后端返回 500。

**实测证据**（可稳定复现，curl 直接验证）：
```
POST /api/score/items          (body={}) -> 500 {"message":"数据访问异常，支持编号 S-20260920113258-e7f6d"}
POST /api/score/entries/batch  (body={}) -> 500 {"message":"系统异常，支持编号 S-20260920113258-d0c26"}
```

**根因**：
- `02-迭代源代码/aigicrm-backend/src/main/java/com/aigicrm/module/score/service/ScoreService.java:55-61`
  `addItem()` **无任何入参校验**，直接把可能全为 null 的实体交给 `itemMapper.insert(item)`，
  触发数据库非空约束异常 → `DataAccessException` → 500。
- `ScoreService.java:128` 起的 `batchSave()` 同类：`period` 为空时未做前置校验即进入写库。

**影响**：非法输入未在边界被拒（应 400），而是以 500 + 数据访问异常暴露，既污染错误语义又可能写入半成品数据。

**建议**：在 `addItem`/`batchSave` 入口补非空/合法性校验并抛 `BusinessException(400, ...)`。

### D-03【Medium】`GET /api/system/perm-scopes/`（空主体键）→ 404，且被空 catch 静默吞掉

**实测证据**（`out_admin.json`，路由 `/system/config` + Tab 权限管理，按钮「刷新」）：
```
GET http://localhost:3000/api/system/perm-scopes/  -> 404
```

**根因链**：
- `views/system/PermScopeManager.vue:229-234`：`loadAll()` 遍历全部角色调用 `loadScopesFor('ROLE', role.roleCode)`；
- `views/system/PermScopeManager.vue:157-158` → `api/system.js:193` `GET /system/perm-scopes/${roleCode}`；
  当 `roleCode` 为空时拼出带尾斜杠的 `/system/perm-scopes/` → 后端无此映射 → 404。
- **放大器**：`PermScopeManager.vue:165` 是**空 `catch {}`**，异常被完全吞掉，页面只表现为"范围列空白"，用户与开发者都看不到失败（违反 AGENTS.md「禁止吞异常/空 catch」）。同类写法还有 `composables/usePermissionData.js:131`。

**复现状态（如实披露）**：该 404 在总计 477 次请求中出现 **1 次**，我随后 3 次定向复现（含完整 7-Tab 序列）**均未重现**；且当时角色表 4 条 `role_code` 全部非空（`0/06/admin/05`）。因此**触发条件尚未确定**，但该请求客观发生过、`catch{}` 客观存在。

**建议**：① `loadScopesFor` 增加空键短路；② 把空 catch 改为至少记录错误并提示（不得继续静默）。

### D-04【Medium】8 个「死权限码」：权限矩阵可勾选，但后端无任何消费方

对 75 个字典权限码与全后端 Java 源码（`@PreAuthorize` 注解 **+ 方法体内 `SecurityUtils.hasAuthority(...)`**，剔除注释行）交叉比对，以下 8 个码在后端**零真实引用**：

| 权限码 | 归属模块 | 说明 |
|---|---|---|
| `customer:share` | 客户 | 客户分享实际走向另一套判定 |
| `incentive:delete` | 激励 | 无消费方 |
| `incentive:manage` | 激励 | **语义漂移**（见下） |
| `incentive:view-all` | 激励 | 已废弃（2026-08-16 授权表化） |
| `incentive:view-shared` | 激励 | 已废弃（同上） |
| `sea:pool:delete` | 公海 | 已被池级 `PERM_DELETE` + `sea:view` 取代 |
| `statistics:scoreboard` | 统计 | 无消费方 |
| `system:menu:edit` | 系统 | 菜单树只读，无编辑端点 |

**`incentive:manage` 的额外发现（文档与现实不符）**：`security/SecurityUtils.java:110-111` 的 javadoc 明确宣称
「`isSalesDirector` 已删除……统一改判权限码 `hasAuthority("incentive:manage")`（M1 绑定给 admin+销售总监）」，
但 `incentive/controller/IncentiveController.java:88-93` 的实际判定是 `incentiveService.canEdit()`，
而 `canEdit()` 走的是 **`biz_incentive_grant` 授权表**，与 `incentive:manage` 无关。
即：**文档声称的"改判到权限码"从未落地**，该码因此成为死码——这也解释了上一轮"给销售员勾 manage 后仍 403"的实测结果。

**影响**：管理员在权限矩阵勾选这 8 个码**不会产生任何效果**，属"配了不生效"的虚假配置——正是本次审计要防的一类问题。其中 4 个激励码与上一轮 `权限活体验证报告-20260919.md` 第五节遗留建议第 1 条完全吻合。

**建议**：从 `sys_menu` 下线死码（新迁移），或在矩阵中对无消费方的码禁用勾选并标注真实控制面；同时修正 `SecurityUtils.java:110-111` 的误导性注释。

> **勘误**：本报告初版曾把 `sea:claim` 也列为死码，经复检**系误判**——该码在
> `module/approval/service/ApprovalService.java:214` 被真实消费（`!SecurityUtils.hasAuthority("sea:claim")`，
> 作为池级权限的存量兼容兜底）。初版误判原因是 grep 只匹配了单引号形式，漏掉双引号调用。详见第九节。

### D-05【已撤回·非缺陷】`contact:view` / `customer:date:edit` 实为后端强制

初版报告称这两个码"只有前端门控、后端无强制"。**复检证明该结论错误，特此撤回**：

```
module/customer/controller/CustomerController.java:345
    if (!SecurityUtils.hasAuthority("contact:view")) return Result.ok(List.of());
module/customer/service/CustomerService.java:513
    return SecurityUtils.isAdmin() || SecurityUtils.hasAuthority("customer:date:edit");
```

两者均在**后端方法体内真实校验**，属正常实现（只是未用 `@PreAuthorize` 注解，形式上与 D-06 同类）。
初版误判原因同 D-04：grep 只查了单引号形式。**此条不计为缺陷。**

### D-06【Low】定时任务触发端点用方法内判定，未用 `@PreAuthorize`

`task/ScheduledTaskController.java:18-25` 的 `POST /api/system/task/check-expire` 无 `@PreAuthorize`，改在方法体内 `if (!SecurityUtils.isAdmin()) throw new BusinessException(403,...)`。

## 四、正向结论（已验证对应用关系成立）

1. **前端 api 层零断链**：181 个 api 函数 **全部**命中后端 212 端点中的真实映射，**0 个 404 风险**。
2. **后端权限码无孤儿**：后端真实引用的 **67** 个权限码（含 `@PreAuthorize` 注解 **与方法体内 `SecurityUtils.hasAuthority(...)` 调用**，剔除注释后统计）**100%** 存在于 `sys_menu` 字典 → 不存在"引用了字典里没有的码导致无人持有该权限、功能恒不可用"这一高发缺陷。
3. **无裸奔端点**：212 端点中 16 个无 `@PreAuthorize`，逐一核对**全部**为登录态/自助/白名单公开（`auth/login`、`auth/info`、`configs/public`、`configs/logo`、`forgot-password/*`、`download-token`、`change-password`（仅操作本人）、`incentive/permission/check`（本人自检）、`common/scope/*`（SecurityConfig 要求 authenticated）），另有 D-06 一例方法内兜底。
4. **代表性的按钮→接口活体接通**（补全表单后逐一实测）：

| 角色 | 页面 | 按钮 | 实测落到的接口 |
|---|---|---|---|
| admin | 审批管理·审批中 | 通过/驳回 | `GET /api/approval/{id}` |
| admin | 任务 | 完成 | `POST /api/task/1/complete` |
| admin | 任务 | 取消 | `POST /api/task/2/cancel` |
| admin | 客户列表 | 导出 | `GET /api/customer/export` |
| admin | 客户列表 | 释放/归档/删除 | `POST /api/customer/...`、`DELETE /api/customer/{id}` |

| admin | 权限规则/角色/岗位/部门/集团 | 增删改 | `system/rule|roles|positions|depts|groups` 系列 |

## 七、建议处置顺序

## 九、第二轮复检勘误（2026-09-20 下午）

应"再检查一下"要求做了独立复检，**发现并纠正了初版报告自身的两处方法学错误**，一并披露如下。

### 错误根因

初版统计"权限码是否有消费方"时，使用了 `grep -F "'<码>'"` —— **只匹配单引号**。
但本项目后端大量使用 `SecurityUtils.hasAuthority("xxx")` **双引号**写法，因此所有这类调用被漏检，
直接导致 2 条结论失真。

### 更正内容

| 条目 | 初版结论 | 复检结论 | 依据 |
|---|---|---|---|
| D-04 死码数量 | 9 个 | **8 个**（移除 `sea:claim`） | `ApprovalService.java:214` 真实消费该码 |
| D-05 前端-only 码 | 2 个码无后端强制 | **撤回，非缺陷** | `CustomerController.java:345`、`CustomerService.java:513` 均在后端校验 |
| 后端引用码总数 | 60（仅注解） | **67**（注解 + 方法体） | 修正扫描口径后重算 |

### 复检采用的新口径（可复现）

对 75 个字典码逐个扫描全后端 Java：**同时匹配单/双引号**，并**剔除 `//`、`*`、`/*` 开头的注释行**，
分别归类为「`@PreAuthorize` 注解引用」「方法体 `hasAuthority` 代码引用」「仅注释提及」。结果：

```
后端真实引用的权限码数: 67
【后端引用但字典无此行】= 0        ← 正向结论，无"功能恒不可用"缺陷
【字典有码但后端零引用(真·死码)】= 8
    customer:share, incentive:delete, incentive:manage,
    incentive:view-all, incentive:view-shared, sea:pool:delete,
    statistics:scoreboard, system:menu:edit
```

### 复检额外带来的两项增强

1. **D-01 定位精确化**：403 实际发生在 **权限管理** Tab（`权限体系` Tab 为静态文案、本身不报错）；
   且失败被静默吞掉（`usePermissionData.js:124-125` 只置位标志、界面无提示），页面渲染成"空矩阵"。
2. **D-04 新增子发现**：`incentive:manage` 的 javadoc（`SecurityUtils.java:110-111`）声称已用它替代
   `isSalesDirector`，但实际判定走 `biz_incentive_grant` 授权表 —— **文档承诺的改判从未落地**，
   这正是上一轮"勾 manage 仍 403"的根因。
