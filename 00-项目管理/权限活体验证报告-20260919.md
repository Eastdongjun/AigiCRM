## 二、四项激励的真实权限模型(实测还原)

```
谁能进激励页/看记录     = incentive:view 勾选(矩阵生效)
能看到哪些记录          = 本人记录 ∪ 已分享记录(全员默认可见)
                          ∪ 全部记录(仅 biz_incentive_grant.can_view_all=1 或 admin)
能否编辑/删除他人记录   = biz_incentive_grant.can_edit / can_delete = 1 或 admin
                          (本人记录恒可编辑/删除,与勾选无关)
```

实测:授权表唯一持有人 NO001(销售总监)can_edit=1 → 编辑他人记录 200;TY002(销售员)无授权行 → 403;给销售员勾矩阵 manage 后依旧 403。
前端/小程序对齐:GET `/api/incentive/permission/check`(grant-check)四开关与上述行为一致,小程序详情页已消费。

## 四、缓存/联动机制实测结论(回应「PC 改了小程序能否生效」)

- **经界面改**(角色勾选/范围下拉):后端 evictAll + permVersion 递增 → 旧 token **下一请求即生效**(实测 403/277 均为旧 token 感知)。
- **直改数据库**(迁移/DBA):必须递增 perm_version,否则最长残留 10 分钟 TTL;**重启应用无效**(Redis 外置)。
- 小程序与 PC 同用 JWT + `/api/auth/info` 权限集,实测 info 已含新绑定码。

## 数据范围的真实优先级(实测确认)

**用户级覆盖(data_scope_override / role_perm_scope USER 行)> 角色级矩阵(ROLE 行)> 角色默认 data_scope。**
行政 NM100 是活例子:她的 `data_scope_override=custom` + `sys_user_org={6,7}` 优先于角色矩阵里 ROLE 05 的 `* *` office 行——在「按角色」Tab 改她的通配范围**不会有任何效果**(属设计正确的覆盖关系),要在「按用户」Tab 改才生效(实测 82↔0↔82)。管理员排查"改了不生效"时先看该用户是否有个体覆盖。
