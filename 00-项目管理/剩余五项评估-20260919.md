## PR-10:跟进记录与下一步任务衔接(P1/P2)

**总册要求**:跟进支持本次结果、下一动作、责任人、计划时间及完成条件;简单记录可不生成任务;明确承诺可形成待办。

**现状**:
- `BizCustomerLog` 仅 6 字段(id/customerId/userId/logType/content/createdAt),**无任务字段**;
- 无任务表、无任务 API、无任务页面。

**缺什么**:
- `biz_task` 表(标题/关联客户/责任人/计划时间/完成条件/状态/来源跟进ID);
- 任务 CRUD API + 列表/统计端点;
- 跟进日志表加 `next_action/due_date/assignee_id` 字段(可选填);
- PC 工作台/小程序首页加待办入口。

**依赖**:无业务决策阻塞(总册已定"简单记录不生成任务,承诺形成待办"的口径),但**工程量大**(新模块)。

**建议**:⚠️ **可做但建议后置**——这是全新模块(表+API+双端UI),建议单独排一个完整迭代;当前优先做下面几项投入产出比更高的。

## PR-18:台账确认、更正、来源与对账(P1)

**总册要求**:录入—待核对—确认—更正/作废—重算闭环;重复导入不重复累计。

**现状**:
- `BizInvoice` 字段:id/customerId/invoiceDate/invoiceNumber/invoiceType/invoiceCompany/amount/createdBy——**无确认状态、无来源标记、无更正记录**;
- 开票/回款直接增删,没有"待核对→确认"流转。

**缺什么**:
- `status` 字段(pending/confirmed/voided);
- `source` 字段(manual/import/sync);
- `corrected_by/corrected_at/correction_reason` 更正留痕;
- 确认/作废 API(确认后锁删,作废保留记录);
- 统计口径:未确认数据是否计入(总册"按明示口径参与或排除")。

**依赖**:确认流程需要财务岗位角色配合(谁有权确认?),但核心状态机可以先做。

**建议**:✅ **可做,建议分两步**——第一步:加状态+来源+更正字段+确认/作废API(后端,可测试);第二步:前端台账页面(待财务确认UI设计)。

## PR-19:附件核对、异常展示与恢复(P1)

**总册要求**:按目标环境核对文件元数据、本体和业务引用;区分可用、缺失、损坏、恢复中、无权限。

**现状**:
- 本地库 1084 条附件元数据,磁盘仅 2 个目录(几乎全部缺失);
- 无核对工具、无异常状态展示。

**缺什么**:
- 对账 API:遍历元数据→检查磁盘文件存在→输出缺失/损坏清单;
- 异常展示:文件列表标记状态(可用/缺失/无权限);
- 恢复:需目标环境备份源(运维层面)。

**依赖**:"恢复"需目标环境的备份文件来源;本地只能做核对工具和异常标记。

**建议**:✅ **核对工具可做**——对账 API + 异常状态展示(后端+小程序文件页标记);"恢复"挂运维。

## PR-21:有效权限解释与授权变更预览(P1/P2)

**总册要求**:增加最终权限解释(当前集团、角色、任职、动作和字段范围、命中规则及阻断原因);授权变更先展示影响。

**现状**:
- `SecurityUser` 已有 `permissionRules` 和 `ruleResult`(规则求值缓存);
- `UserDetailsServiceImpl.loadUserByUsername` 完整计算权限链(角色→规则→范围→覆盖);
- **已有 `/api/auth/info` 返回 permissions 列表和 dataScope**。

**缺什么**:
- **权限解释端点**:不只返回"有什么权限",还要返回"为什么"(哪些角色/规则命中);
- 授权变更预览:修改角色前展示"将影响 N 个用户,新增/失去哪些权限"。

**依赖**:PR-06 权限分离(已完成主体)。

**建议**:✅ **可做,投入产出比最高**——现有权限计算逻辑完整,只需加"解释输出"层:读取 ruleResult + permissionRules 结构化输出;变更预览需要对比新旧权限集合。
