# 代码评审流程 v1（2026-11-23）

> 配套标准：`docs/code-review-standard-20261123.md`（分级 R0–R3、维度 D1–D8、一致性基线 §4）
> 本文只解决一件事：**谁在什么时候、按什么顺序、拿什么证据，判定"可以合"。**

---

## 0. 现实前提（先说清楚，否则流程是空转）

本仓库 50 次提交全部来自同一个作者（`Eastdongjun` / 东君），**没有第二个人可做独立评审**。

因此照搬"作者提 PR → 另一人 approve"是**形式主义**：要么自批自过，要么卡死。

本流程按单人仓库设计，把"评审"拆成三个**可独立执行、可留痕**的动作：

| 动作 | 执行者 | 作用 | 证据 |
|---|---|---|---|
| **A 机械自检** | 作者跑脚本 | 把 L1/L2 问题清零 | `gate.sh` 输出 |
| **B 结构化自审** | 作者按清单过 | 强制在提交前回答 D1–D8 | PR 模板勾选 + 说明 |
| **C 独立评审** | **Agent / 外部评审者** | 提供作者视角之外的判断（作者自审有系统性盲区） | 评审报告（R0–R3 + 文件:行） |

> 关键点：**B 不能替代 C**。作者写代码时的假设，自己再审一遍仍然是同一套假设。
> C 的价值不在"多一双眼睛"，在"换一套假设重新推一遍"。所以 C 必须**不预设立场**、按证据说话。

## 1. 状态机

```
CR0 草稿 ──► CR1 机械自检 ──► CR2 结构化自审 ──► CR3 独立评审 ──► CR4 整改 ──► CR5 门禁 ──► CR6 合并
                │                  │                  │                │            │
                └── 红 ────────────┴── 缺项 ──────────┴── R0/R1 ───────┴── 红 ──────┘
                                  (退回上一状态，不跳级)
```

| 状态 | 进入条件 | 完成条件（出口） | 谁执行 |
|---|---|---|---|
| **CR0 草稿** | 代码能编译 | 自测通过，改动清单清楚（哪些文件、为什么） | 作者 |
| **CR1 机械自检** | CR0 完成 | `bash scripts/gate.sh` 全绿；L1 层零红 | 作者 |
| **CR2 结构化自审** | CR1 绿 | PR 模板中 D1–D8 全部有明确结论（含"不适用"） | 作者 |
| **CR3 独立评审** | CR2 完成 | 产出评审报告：R0/R1 清单 + R2/R3 台账 + 结论 | Agent/外部 |
| **CR4 整改** | CR3 有 R0/R1 | R0 全清；R1 全清或登记关闭条件 | 作者 |
| **CR5 门禁** | CR4 完成 | `gate.sh` 复跑绿 + Sonar 触碰文件 0 新增 | 作者 |
| **CR6 合并** | CR5 绿 | 提交信息含评审报告路径；证据归档 | 作者 |

**不跳级**：CR1 没绿就进 CR3，等于让评审人替你跑 lint。

## 2. 按改动规模分档（不是所有改动都值得同一套深度）

| 档位 | 判定 | 评审深度 | 典型耗时 |
|---|---|---|---|
| **S 小改** | ≤3 文件 且 无 DB/权限/接口变更 | CR1 + CR2 勾选即可，**免 CR3** | 分钟级 |
| **M 中改** | 4–20 文件，或涉及接口/字典/前端交互 | CR1–CR4 全流程 | 半小时级 |
| **L 大改** | >20 文件，或**涉及 DB 迁移 / 权限码 / 资金或统计口径** | CR1–CR6 全流程 + **必须**独立评审报告 | 半天级 |
| **X 紧急** | 线上故障止血 | CR1 绿 + 事后 24h 内补 CR3 报告 | 先止血后补 |

判定取**最高档**：涉及迁移一律按 L，即使只有 1 个文件。
理由：迁移错误的代价与文件数无关（V2026.09.21.1 就是 1 个文件删了权限行）。

## 3. CR1 机械自检（唯一的执行入口）

**只跑一条命令**，不手工拼检查项：

```bash
cd 02-迭代源代码 && bash scripts/gate.sh          # 完整档，交付前必须
cd 02-迭代源代码 && bash scripts/gate.sh --quick  # 迭代中间自检
```

| 情况 | 处理 |
|---|---|
| 有红项 | **修根因**。禁止关规则/降级/删断言/扩排除（COMMON-04，红线） |
| 依赖缺失（`mvn`/`rg`/`python3`） | 门禁 fail-closed，装齐再跑，**不得跳过** |
| 只改了文档/配置 | 仍需跑，`check-doc-freshness.sh` 会拦滞后文档 |

### 3.1 已知假红（不是代码问题，别去改代码）

| 现象 | 成因 | 处理 |
|---|---|---|
| `[3] 前端构建` 报 `[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":243,...,"targets":[.../aigicrm-ui/dist/assets]}` | Agent 沙箱的批量删除保护拦住了 `vite build` 清空 `dist/assets`（243 文件 > 阈值 50）。**在开发者终端与 CI 上不会出现**。`dist` 已 gitignore，不是源码 | 先 `mv aigicrm-ui/dist /tmp/dist-prev` 再重跑，让 vite 从零生成 |
| `[4] 文档新鲜度` 报 `data-dictionary.md` 落后 | 生成物未重跑 | `bash scripts/gen-data-dictionary.sh` 后重跑 |

> 判据：**假红只允许出现在构建产物清理与生成物新鲜度两类**。其他红项一律按根因修，不得归因为"环境问题"。

补充（按改动类型触发，不属 gate.sh 全集）：

| 改动类型 | 追加命令 |
|---|---|
| 涉及权限/数据范围 | `AIGI_MATRIX=1 bash scripts/gate.sh` |
| 涉及 DB 迁移 | 空库重放：`docker run --rm --network <net> -v <migration>:/flyway/sql flyway/flyway:9.22.3-alpine migrate` |
| 涉及小程序 | `bash scripts/dev-verify.sh miniprogram` |
| 涉及接口 | `python3 scripts/gen-api.py && bash scripts/check-api-list-fresh.sh` |

## 4. CR2 结构化自审（用 PR 模板强制回答）

作者在 PR 描述里逐项填 `D1–D8`，**每项必须有结论**，不允许留空。

写法要求：

- 不适用就写"不适用 + 原因"，例如：`D5 性能：仅改文案，无查询变更 → 不适用`；
- 有风险就写风险 + 接受理由，例如：`D3 单一源：复用 FabushiScopeType，未新增字面量`；
- **禁止只勾复选框不写字**。勾选不产生信息。

## 5. CR3 独立评审（本流程的核心产出）

### 5.1 输入

| 输入 | 用途 |
|---|---|
| 改动文件清单 + diff | 评审对象 |
| PR 描述（含 D1–D8 自审结论） | 对照"作者以为的"和"代码实际的" |
| `docs/code-review-standard-20261123.md` | 判定依据，不自创标准 |
| `gate.sh` 输出 | 确认 L1 已绿，不重复查 |

### 5.2 执行顺序（按风险从高到低，不按文件顺序）

```
1. 迁移/DDL        → 数据不可逆，最先看
2. 权限与归属       → 越权代价最高
3. 事务与状态机     → 脏数据来源
4. 入参与错误语义   → 线上 500 与误导性提示
5. 单一源与一致性   → 双端漂移
6. 性能与规模       → N+1 / 无分页
7. 测试充分性       → 断言是否真的能失败
8. 可维护性         → 文件规模 / 命名 / 注释
```

### 5.3 输出格式（固定，便于归档与复查）

```markdown
## 评审结论：PASS / PASS WITH NITS / REJECT

### R0 阻断（必须改完才能合）
- [文件:行] 问题描述 → 后果 → 建议修法

### R1 必修
- [文件:行] 问题描述 → 后果 → 关闭条件

### R2 建议
- [文件:行] 问题描述 → 影响

### R3 记录
- 观察项，不构成修改要求

### 做得好的（必须写，用于固化正面模式）
- 具体到文件/做法，不写空话
```

**要求**

- 每条必须有 **文件:行**，否则不是发现，是印象。
- **必须写"做得好的"**：只挑错会让标准退化成挑刺，无法沉淀正面模式。
- 结论只能是三档，禁止"基本通过""问题不大"。

### 5.4 反偏误要求

| 偏误 | 防范 |
|---|---|
| 只评新代码不看改动邻居 | 增量评审必须做**影响扩展**（COMMON-06）：改了 A 要看调用 A 的 B |
| 把 L1 问题当发现 | 先看 `gate.sh` 是否绿，绿了就别再提格式/复杂度 |
| 提"建议重构"但不说收益 | R2 必须写清影响，否则降为 R3 |
| 用"我觉得"下判断 | 每条判定必须能指向标准里的维度/规则编号 |

## 6. CR4 整改规则

| 级别 | 要求 |
|---|---|
| R0 | **全清**，不允许"下个迭代" |
| R1 | 全清；确需延后必须写：关闭条件 + 责任人 + 复查时点，并进 `TEST-FINDINGS-*.md` |
| R2 | 登记进 `docs/TECH_DEBT.md` 或本迭代台账，不要求当期修 |
| R3 | 仅记录 |

**整改后必须复跑 `gate.sh`**，不能凭"我改了"就认为好了。

## 7. CR5 门禁（与既有体系的接线点）

| 检查 | 命令/来源 | 通过标准 |
|---|---|---|
| 交付全集 | `scripts/gate.sh` | 全绿 |
| 单任务出口 | `scripts/quality-gate.sh` | 全绿（与 gate.sh 分工见 `test-gate-template-20261122.md §0`） |
| Sonar | `mvn sonar:sonar` + issues API | **触碰文件** 0 新增 OPEN；质量门状态如实记录（当前 ERROR 为存量） |
| 密钥 | `sonar analyze secrets <files>` | 0 问题 |
| 测试矩阵 | `TEST-MATRIX.yaml` | 新增能力有对应用例，状态如实（blocked 不得写成 pass） |

**如实性要求（不可妥协）**

- 质量门 ERROR 就写 ERROR，不得用"新代码没问题"掩盖整体未过；
- blocked 就写 blocked + 阻塞原因，不得写 pass；
- 未执行的验证不得出现在"已验证"里。

## 8. CR6 合并

提交信息必须能让**没参与的人**看懂，格式：

```
<type>(<scope>): <一句话结论>

- 变更：做了什么
- 原因：为什么（关联需求编号/事故编号）
- 验证：跑了什么，结果如何
- 评审：CODE-REVIEW-YYYYMMDD.md（结论 + R0/R1 数量）
```

`type`：`feat` / `fix` / `refactor` / `perf` / `test` / `docs` / `chore` / `migration`

**拆分原则**：一个提交一个可独立回滚的意图。迁移与其对应代码**必须同提交**。

## 9. SLA 与争议

| 场景 | 时限 |
|---|---|
| CR3 独立评审（M 档） | 提交后 1 个工作日内出报告 |
| CR3 独立评审（L 档） | 2 个工作日内 |
| R0 整改 | 立即，阻塞合并 |
| R1 整改 | 本迭代内 |
| X 档补评审 | 止血后 24 小时内 |

**争议升级**：作者与评审结论不一致时，**不投票、不搁置**，按以下顺序裁决：

1. 回到标准找条款 —— 标准有明确规定的，按标准；
2. 标准未覆盖 —— 补一条标准（同时修订本文 §8 版本表）；
3. 涉及业务口径 —— 由用户（需求方）拍板，结论写入需求文档。

> 第 2 条是本机制能自我进化的关键：**每次争议都必须留下一条新规则**，否则同样的争论会重复发生。

---

## 10. 例外通道（X 档）

仅限线上故障止血，且必须满足：

1. 有明确的故障现象与影响面（不是"感觉要坏了"）；
2. 变更范围最小化（只改止血必需）；
3. `gate.sh --quick` 绿；
4. **24 小时内补 CR3 报告**，并在报告里说明"当时的取舍"。

不满足第 4 条 → 视为流程违规，需在下次评审中复盘。

## 11. 落地检查表（第一次用就照这个走）

```
□ 1. 建 PR，选档位（S/M/L/X）

□ 6. CR5：gate.sh 复跑 + Sonar 触碰文件 0
```
