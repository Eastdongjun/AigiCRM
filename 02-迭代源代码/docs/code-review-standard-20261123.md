# 代码评审标准 v1（2026-11-23）

> 配套流程：`docs/code-review-process-20261123.md`
> 上位规则：`.audit/rules/`（安全/Java/通用等）、`docs/test-gate-template-20261122.md`（G0–G7 测试门禁）
> 本文只解决一件事：**"什么样的代码算过，什么样的不算"**，且判定口径可复现。

---

## 0. 现状诊断（为什么需要这份标准）

本仓库的**自动化**已经很强，缺的是**判断层**。实测数据：

| 资产 | 数量 | 说明 |
|---|---|---|
| 契约检查脚本 | **113** 个 `scripts/check-*.sh` | 权限/菜单/迁移/接口/双端一致性等 |
| 一键交付门禁 | `scripts/gate.sh`（180 行） | 后端全量 + 前端 + 小程序 + contracts + 文档新鲜度 |
| CI | `.github/workflows/ci.yml`（397 行） | PR 触发，含 ArchUnit 分层约束 |
| 单测 | 后端 1290、前端 364 | 断言密度 2–4/用例，健康 |
| Sonar | 本地 + SonarCloud | 质量门当前 **ERROR**（存量） |

**问题不在"没检查"，在"检查完了没人对判断类问题负责"**：

- 没有 PR 模板 → 每个提交自带的信息量取决于当天心情，评审无从下手；
- 没有严重度分级 → "这个要不要改"全靠感觉，导致同类问题一次拦一次放；
- 没有一致性基线 → 同一个语义在代码里有 2–4 种写法（见 §4 实测）；
- 没有证据留痕 → 事后无法回答"当时为什么允许这样合"。

**目标不是增加流程，是把已有 113 个脚本 + Sonar 判不了的那部分判断，变成可复现的判定。**

## 1. 与既有体系的分工（先划清，避免重复劳动）

| 层次 | 归谁 | 管什么 | 评审时怎么做 |
|---|---|---|---|
| L1 机器可判 | 113 契约 + Sonar + ArchUnit + 单测 | 命名/格式/复杂度/分层/契约/安全规则 | **不人工复查**，只看 `gate.sh` 是否绿 |
| L2 机器半可判 | 本标准的 §4 一致性基线 | API 用法、常量命名、异常风格、返回风格 | 用 §4 的清单**扫一遍**，不靠印象 |
| L3 只能人判 | 本标准的 §3 维度 | 设计是否合理、边界是否想全、业务语义是否正确、可维护性 | **评审的主体时间花在这** |

> 铁律：**L1 没绿不进入 L3。** 让评审人把时间花在 lint 能查的事上，是最大的浪费。

## 2. 严重度分级（R0–R3）

判定依据是**后果**，不是"看起来难不难改"。

| 级别 | 定义 | 处理 | 举例（本仓库真实场景） |
|---|---|---|---|
| **R0 阻断** | 会导致数据错误/越权/资金或权限错乱/线上不可用 | **必须改完才能合**，无例外 | 写端点缺服务端权限复核；迁移按硬编码 id 定位行（历史事故 V2026.09.21.1 全员 403）；多表写无事务 |
| **R1 必修** | 功能在正常路径可用，但在异常/边界路径产生错误行为或错误状态码 | **本迭代内必须改**，可先合但需登记 | 入参非法时返回 500 而非 400；单一源规则被绕过导致双端不一致 |
| **R2 建议** | 不影响正确性，但增加后续维护成本 | 可排期，需登记 | God class；同一语义两种 API 混用；机械命名常量 |
| **R3 记录** | 观察项/待确认，不构成修改要求 | 仅记录 | 兜底文案永不生效；注释声明"由 X 兜底"但 X 覆盖面未验证 |

**分级纪律**

- 不允许"降级了事"：把 R0 说成 R2 是最常见的自欺。判不准时**往高判**。
- 不允许"记录代替修复"：R0/R1 不能只写进台账。
- R0 的认定不接受"历史就这样"——历史遗留按 `§6 存量豁免` 走，不按"习惯了"走。

## 3. 评审维度（L3，人工必查）

每个维度给**判定问句**，评审时逐条回答"是/否/不适用"，避免空泛。

### D1 权限与数据边界（最高优先）

- 每个写端点是否 `admin ∨ 功能权限码 ∨ 对象归属` 三选一守卫？（对应 SEC-10）
- 路径参数对象（id）是否做了**归属校验**，而不只是功能码？（SEC-11）
- 列表/统计/导出/提醒四条链路是否都带租户过滤？（SEC-13）
- 前端隐藏是否被误当成权限？（前端隐藏 ≠ 授权）

### D2 事务与状态一致性

- 多表写是否在**同一事务**？跨服务调用是否会出现"主表成功、子表失败"？
- `@Transactional` 是否落在**真正被外部调用的入口**上（不是被同类自调的私有路径）？
- 状态机非法迁移（已下架再编辑、审批中删除）是否被**服务端**拒绝？

### D3 单一源与契约

- 同一业务枚举/字典，是否只有**一个**定义处？双端是否引用同一源？
- 新增/改动的接口是否同步了 `api-list`、权限码、数据字典？
- 前端常量与后端枚举是否同名同值（本仓库靠 `check-fabushi-scope-types.sql` 兜底）？

### D4 输入校验与错误语义

- 入参是否**声明式校验**（DTO + `@Valid`）？若用 `Map<String,Object>` 手工解析，非法类型是否转成 **400** 而不是 500？
- 业务拒绝是否抛 `BusinessException(code, msg)`（JAVA-03）？是否有人抛裸 `RuntimeException` 导致文案被兜底吞掉？
- 错误信息是否**指向用户可行动**（"已下架内容不可编辑"）而非技术术语？

### D5 性能与规模

- 是否引入 N+1（循环内查库）？批量是否走 `selectByIds` 一次取回？
- 列表端点是否有分页上限？导出是否可能全表拉取？
- 大字段/附件是否在列表接口被无意查出？

### D6 可维护性

- 单个类/文件是否超过 **600 行**（超出需给出拆分理由）？
- 单个方法认知复杂度是否被 Sonar 判 CRITICAL（S3776）？
- 命名是否表达**意图**（`LIT_X_2` 这种不行，见 §4）？
- 注释是否解释**为什么**，而不是复述代码？

### D7 测试

- 新增/改动的行为是否有对应用例？**只测 happy path 视为未测**。
- 每个用例是否有实质断言（Sonar S2699 零容忍）？
- 边界用例是否覆盖：空、越权、状态非法、并发/幂等？

### D8 前端/小程序专项

- 是否有 `console.log` / `debugger` 残留？
- 空 `catch` 是否**验证过**兜底方真实覆盖（COMMON-03）？
- 交互是否处理 loading / 空态 / 错误态三态？
- 是否影响无障碍（键盘可达、`aria-label`、`prefers-reduced-motion`）？

## 4. 一致性基线（治"质量不一致"的直接药方）

这一节是**可机械扫的清单**，评审时按清单过，不靠印象。每条都给本仓库的实测反例。

### 4.1 常量与枚举：一个语义一个源

| 规则 | 实测反例（2026-11-23） |
|---|---|
| 业务枚举的 code 禁止在别处重新写字面量 | `FabushiScopeType` javadoc 明写"双端字面量禁止另行定义"，但 `FabushiBookService:82-83` 用裸 `"suishi"`/`"songdu"`；`FabushiReadingService:42-43` 自建 `SCOPE_SONGDU`/`SCOPE_SUISHI` |
| 常量名必须表达语义 | `FabushiPostService:51` `LIT_X_2 = "内容不存在"` —— 这是为消 Sonar S1192 机械抽出来的，名字零信息量 |
| 同类常量命名统一前缀 | `LIT_*` / `SCOPE_*` / `DICT_*` 三种前缀并存，需在模块内统一 |

### 4.2 数据访问 API：一个语义一个方法

| 规则 | 实测反例 |
|---|---|
| 批量按 id 取一律用 `selectByIds`（`selectBatchIds` 已弃用） | 主代码仍有 **31** 处 `selectBatchIds`，与 `selectByIds` 混用 |
| 查询条件用 Lambda，禁止字符串列名 | 已由 JAVA-02 覆盖，Sonar 兜底 |

### 4.3 异常与返回

| 规则 | 实测反例 |
|---|---|
| 业务拒绝抛 `BusinessException`，禁止裸 `RuntimeException` | `JwtTokenProvider:202` 抛 `new RuntimeException("注销失败：…")`，被 `GlobalExceptionHandler` catch-all 吞成 `500 系统异常`，**这句文案永远不会到达用户** |
| 统一用 `Result.ok` / `Result.error` | 已统一（345 / 20），保持 |
| 状态码语义固定：400 参数、401 未登录、403 无权、404 不存在、409 冲突、429 限流 | 现状 400×138 / 403×120 / 404×42 / 401×17，语义清晰，保持 |

### 4.4 入参解析：一个入口一个策略

| 规则 | 实测反例 |
|---|---|
| 优先 DTO + `@Valid`；确需 Map 时，**所有**类型转换必须走统一 helper 并转 400 | `Map<String,Object>` 手工解析散落 **11+** 处；`FabushiReadingService:461,466` 已有 `parseLong/parseInt` helper 但**未被其他文件复用**；`FabushiBookmarkController:32` 裸 `Long.valueOf(String.valueOf(...))`，非法值直接 500 |

### 4.5 分层与文件规模

| 规则 | 实测反例 |
|---|---|
| Controller 不返回实体（ArchUnit 已钉） | 已受约束，保持 |
| 单文件 > 600 行需在 PR 说明拆分计划 | `RecycleService` 1194、`recycle.vue` 1021、`FolderPermissionService` 812、`FabushiPostService` 681 |

### 4.6 前端脚本风格

| 规则 | 实测 |
|---|---|
| 统一 `<script setup>` | ✅ **103/103 全部一致**，这是本仓库做得最好的地方，评审时无需再查 |

> 基线维护方式：本节每条若被机器化（新增 `check-*.sh`），则从人工清单**移出**并在此标注脚本名。
> 目标是把 §4 逐年清空，人工评审只留 §3。

## 5. 反模式清单（来自本仓库真实事故）

评审看到以下形态**直接按 R0/R1 处理**，不必讨论：

| 反模式 | 后果（实证） |
|---|---|
| 迁移里按硬编码行 id 定位/删除 | V2026.09.21.1 误删 task 权限行 → **全员 403** |
| 守卫写成 `if (isOrgAdmin() && !canManageUser(id))` | 对非管理员**整体短路** → 越权（DeepSeek P0-1） |
| 注释写"由 X 兜底"但 X 不存在/不覆盖 | 门禁假绿，问题在生产暴露（COMMON-03） |
| 关规则/降级/删断言/扩排除来让门禁变绿 | 门禁失去意义（COMMON-04，本仓库明令禁止） |
| 迁移引用不存在的列，且守卫写在 `IF()` 未命中分支 | MySQL **解析期**就报错，任何库都跑不过（2026-11-23 实测） |
| 跨 collation 比较（`general_ci` vs `0900_ai_ci`） | 1267 迁移中断（2026-11-23 实测） |
| 同类自调 `@Transactional` 方法 | 代理被绕过，事务靠外层侥幸（S6809，2026-11-23 实测） |

## 6. 存量豁免（不是免死金牌）

- 豁免只对**已存在**的问题生效，且必须登记在案：文件、行、规则、理由、关闭条件。
- **新增代码不适用豁免**。改动一行就算触碰，触碰即按本标准评。
- 豁免清单的单一源是 Sonar 的 `sonar.issue.ignore.multicriteria`（如 `java:S1068` 对 entity/dto/security）
  与 `.audit/rules/` 里的祖父条款（如 INV-MIG-001 的 allowlist）。**不得在别处另建口头豁免。**

---

## 7. 判"不通过"的红线（一票否决）

出现任一条，评审结论直接 **REJECT**，不进入讨论：

1. 写端点缺服务端权限/归属校验；
2. 迁移或数据修复脚本按硬编码 id 定位行；
3. 多表写无事务，或事务边界落在错误层级；
4. 为让门禁变绿而关规则、降级、删断言、扩排除；
5. 测试断言被删除或注释掉；
6. 凭据/密钥入库或入证据文件；
7. 文档声明与代码实际能力不符（如宣称已实现真推送但只是红点）。
