# 提醒体系

> 来源锚点:`ReminderService`(expiringPage/ensureExpiring/process/pendingCount)、`CustomerExpireTask`。核实日期 2026-10-08(2026-09-24 完成双去重口径统一与 401 条积压清理,V2026.09.23.8;2026-10-08 对齐 30 天窗口边界并补记 invoice_never 宽限期)。

## 1. 提醒类型(六种)

| 类型 | 触发条件 | 生成方 |
| --- | --- | --- |
| `expiring` 到期提醒 | 客户 expire_date 进入 30 天窗口(未到期,**含第 30 天**;【修复 2026-10-08】凌晨任务与页面/角标/补生成已对齐同一含边界口径) | 凌晨任务 + admin 手动补生成 |
| `invoice_overdue` 开票超期 | 已开票但最近开票日距今 > 365 天 | 凌晨任务 |
| `invoice_never` 从未开票 | 从未有过开票记录,**且建客超过宽限期**(系统设置 `invoice.never.grace.days`);【修复 2026-11-02】宽限基准=**register_date(业务注册日,原为 created_at 入库时间)**,NULL 回退 created_at;默认宽限=**365 天**(原 30,对齐"新客户按注册日有一年保护期,保护期内不催首次开票";2026-11-02 口径A 一年=365);0=无宽限 | 凌晨任务 |
| `share_to` 客户已分享给你 | 分享发生时 | 业务动作 |
| `share_by` 你分享了客户 | 分享发生时 | 业务动作 |
| `share_owner` 你的客户被分享 | 分享发生时 | 业务动作 |

## 2. 物化与去重(09-24 统一判据)

**统一判据:该客户存在 status=pending 的 expiring 提醒,或今日已有 processedAt 落在今天的记录 → 不新建。**

- 修复前双口径打架:凌晨任务"无 pending 才建" vs 页面补生成"今日没建过就建"→ 页面每触发一次多造一条,旧 pending 永不清,生产积压 401 条。
- 两个写入方(凌晨 `CustomerExpireTask` 与 admin 手动 `POST /reminder/ensure-expiring`)现在同一判据;`ensure-expiring` 为 **admin-only**(P1-09 收紧,PC/小程序前端均已对齐:非 admin 不触发)。
- 补生成仅对 admin 有意义,普通用户的数据新鲜度由凌晨任务兜底,不依赖任何人在页面上点。

## 3. 跟进语义

- `process(id)`:置 processed + processedAt=now;仅本人范围内提醒可处理(越权报"无权处理")。
- 到期列表行的 `reminderId` 指向该客户**当前 pending 的那条**(无则指向今日已处理那条);`todayFollowedUp` = 今日处理过(processedAt 口径)。
- 处理完当天不再重复物化;**次日**由凌晨任务或 admin 补生成再造一条新 pending,形成每日跟进循环,直到客户移出窗口或入海。
- **裁决 2026-09-24:维持每日轻量循环**(每天一条待办、处理即毕),不加重跟进表单;「跟进结果/下一步」类增强留作 V2。

## 4. 角标

`pendingCount` = 数据范围内未跟进的 expiring 客户数 + 分享类待处理提醒数,驱动侧边栏角标。

## 5. 可见性

按 `reminder` 模块数据范围(resolveModuleUsers);非 all 范围用户只见范围内负责人的提醒;详情页按 ID 猜读有越权防护。

## 6. 死 pending 清理(常驻钩子 + 历史清偿)

- **悬挂 expiring 回收【修复 2026-11-02】**:每晚任务 `recycleStaleExpiringReminders` 回收
  到期日已被推远(延期批准/重新开票刷新保护期)后仍在窗口外的 pending expiring 提醒
  (processed 留痕不物理删,与"发票可删留痕"同一审计口径)——修复前 expiring 只有生成没有
  回收,到期日推远后旧临期提醒永久 pending 挂在工作台(生产实证:张家峁 expire 已推至
  2027-11,10-23 生成的临期提醒仍挂)。
- **常驻清理【体检 P1 2026-10-12,INV-05 全量口径】**:客户删除/归档/入海/捞取四个生命周期钩子
  同批清理该客户**全部类型**的 pending 提醒(CustomerService.cleanPendingReminders);分享撤销仍按
  被移除者清 share_to。此前仅分享类有钩子,expiring/invoice_* 类死行靠一次性迁移清过两轮后重新积压
  (2026-10-12 生产摸底 59 条,V2026.10.12.1 再清偿)。
- **治愈回收**:客户重新开票(阶段录入开票额>0 前移最近开票日)时,pending 的 invoice_never/
  invoice_overdue 即清,由凌晨任务按新事实重建(防「待首次开票/已超期N天(N 冻结)」旧文案误导)。
- 历史清偿:V2026.09.23.8(expiring 去重+死行,生产 401→32)/V2026.10.09.1(分享类)/V2026.10.12.1(全类型)。
- 已知语义缺口(待裁决):分享类提醒建行不带 office_id,部门筛选(IN 子树)下不可见——分享提醒
  按人锚定、办事处归属语义未定义,选"全部部门"即恢复可见。
