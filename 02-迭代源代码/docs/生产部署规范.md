# AIGICRM 生产部署规范（2026-08-15 磁盘架构迁移后生效）

> 本文件是生产环境的**部署宪法**。所有部署、迁移、备份操作必须符合本规范；
> 部署脚本已内置 `check_deploy_arch()` 自检（每次部署开始自动核对，⚠️ 必须人工确认）。
> 偏离本规范前必须先与负责人确认并更新本文件。

## 1. 磁盘三区架构（用户规划，2026-08-15 迁移落实）

| 区域 | 用途 | 路径 | 禁止 |
|---|---|---|---|
| 系统盘 vda（100G） | **只放操作系统** | / | 放程序、数据库、文件 |
| 数据盘 vdb（400G） | **程序 + 数据库**（路径区分） | /data | 放用户文件 |
| NAS（阿里云 NFS） | **用户文件** | /Aigicrm/files | 放程序、数据库 |

### 数据盘标准布局

| 路径 | 内容 |
|---|---|
| `/data/docker` | Docker 根（镜像 + 容器 + 卷），daemon.json 的 `data-root` |
| `/data/database/mysql-data` | MySQL 数据（**独立于程序路径**，bind 挂载到容器 /var/lib/mysql） |
| `/data/aigicrm` | 部署目录（compose/nginx/ssl/部署脚本/jar/日志）；`/root/aigicrm` 为指向它的软链接，旧路径引用全部有效 |

### NAS 标准布局

| 路径 | 内容 |
|---|---|
| `/Aigicrm/files/uploads` | 上传文件（后端 bind 挂载 /app/uploads，**线上真实路径**） |
| `/Aigicrm/files/aigicrm-dist` | 前端静态资源（nginx 容器挂载） |
| `/Aigicrm/files/backup` | 备份区（daily 每日备份 / dist-rollback / jar 备份） |

## 2. 部署流程（一律走仓库脚本，禁止手工 docker run 偏离标准）

```bash
cd /Users/donglai/东来/01-Projects/01-aigicrm/04-源码/02-迭代源代码/scripts
./deploy-frontend.sh   # 前端: Mac 构建 → NAS dist 切换(自动留回滚副本) → 验证
./deploy-backend.sh    # 后端: 测试服已验证 jar → 生产重建镜像 → 重启 → 验证
./deploy-db.sh         # 数据库: 生产自动备份 → Flyway 迁移 → 结构验证
```

- 每个脚本开始自动执行**部署架构自检**（docker 根 / mysql 挂载 / 软链 / NAS 上传），⚠️ 项必须人工确认后再继续
- 健康检查一律用 `~/.aigicrm-deploy.env` 的 `HEALTH_CHECK_USER/PASS`（禁止硬编码密码）
- 部署后必须 `./smoke-test.sh prod` 全绿（PASS=20 FAIL=0）
- 前端源码目录：`04-源码/02-迭代源代码/aigicrm-ui`（08-14 仓库重组后的位置）

### 2.1 大版本发布前例行动作（2026-11-05 用户令纳入）

除常规门禁（dev-verify 各族 + 冒烟）外，**大版本发布前必须执行一轮 Mimosa 深度安全扫描**：

1. **发起**：ZCode 会话内调用 Mimosa 插件 `security_scan_start`（depth=deep）。
   - **大版本**：不带 focusFiles 全仓扫；**小版本/热修**：可带 focusFiles=本批改动文件。
   - project 恒为仓库根（`02-已上线/01-AIGICRM`）。
2. **收数**：`security_scan_status` 拿 scanId/seal/报告目录（`~/.mimosa/security-scans/<project-id>/<scan-id>/report.md`）。
3. **人工分诊（初筛非终审）**：逐条复核 findings——重点甄别三类历史误报形态：
   - "硬编码凭据"命中**运行时 Env 注入的变量赋值行**（如 `export FLYWAY_PASSWORD="$DB_ADMIN_PASS"`）= 误报；
   - 测试夹具的 `require()` 被"命令注入"模式误报；
   - 本地开发工具（gen-*.py 等）的"命令行参数→输出路径"污点链 = 设计使然，非不可信输入。
   - 真实发现才进修复流程；误报结论要在会话记录里留实证（源码行摘录）。
4. **基线对照**：首基线 = `scan-2026-11-05T10-55-50`（seal `sha256:ff2ba4a7…f22f`，13 项全为工具脚本层误报/设计使然，产品代码零发现）。后续扫描与基线比增量，新增项重点看。
5. **归档**：报告目录自带封印（seal.json）天然可复核，无需另行拷贝；会话记录里留 scanId 即可。

> 覆盖声明照抄：静态分析（static_only_no_runtime_execution），调用图部分构建（动态派发不可达属固有边界）；运行状态 inconclusive 不阻断发布，但**产品代码层的真实 HIGH 不允许带病上大版本**。

## 3. 数据库铁律

- **数据必须 bind 挂载 `/data/database/mysql-data`**，禁止用命名卷挂库（防止与程序路径混同）
- 所有 schema 变更走 Flyway：`aigicrm-backend/src/main/resources/db/migration/V10+__xxx.sql` + `deploy-db.sh`；不得原地改 V1
- 变更前脚本自动备份（backup-pre-migrate-*.sql），部署前必须有回滚方案
- 应用账号 aigicrm_app 无 DDL 权限；迁移仅以 root 经脚本执行

## 4. 文件铁律

- 上传文件只存在于 NAS `/Aigicrm/files/uploads`；旧卷 `upload-data`/`aigicrm_upload-data` 是历史回滚副本，**禁止重新挂载**（会"文件消失"）
- 上传文件备份 tar 内含大小写同名文件，**禁止在 Mac（大小写不敏感文件系统）解包**，恢复必须在 Linux 服务器上执行
- 前端 dist 回滚：NAS `backup/dist-rollback-<时间戳>/` 目录内容拷回 `/Aigicrm/files/aigicrm-dist/` 即回滚

## 5. 备份规范

- **每日自动**：02:30 cron `/usr/local/bin/aigicrm-daily-backup.sh` → NAS `backup/daily/YYYYMMDD/`（保留 14 天）；上传文件备份取 `/Aigicrm/files/uploads`（2026-08-15 修复，旧版指向废弃卷）
- **手动全量**：按 `10-正式环境备份/备份清单.md` 的五类产物（源码/数据库/上传文件/配置/镜像）+ 恢复演练
- 恢复方法见各期 `备份清单.md`；数据库恢复先建库（utf8mb4）再导入，演练在测试服 aigicrm-mysql

## 6. 禁止事项（违反即事故）

1. 系统盘放程序/数据库/文件（回滚副本 `/var/lib/docker`、`/root/aigicrm.bak-*` 属临时例外，到期删除）
2. 脚本/注释/仓库中硬编码密码、密钥、生产地址
3. 数据库用命名卷（必须 `/data/database/mysql-data` bind）
4. compose up -d 全量执行（mysql 与 backend 的卷行与运行态一致，但历史容器由 docker run 创建，全量 up 会重建容器偏离运行态；仅用 `up -d mysql` 或按脚本部署）
5. Mac 上解包上传文件 tar
