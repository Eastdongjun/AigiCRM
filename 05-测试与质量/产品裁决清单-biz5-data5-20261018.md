### 2.3 如果选 A，必须先把这些产品规则定下来

A 不是“补一个按钮”，而是补一套制度。最少要拍板：

1. **谁可以发起**：仅本人给自己申请，还是管理员可给任意用户申请？建议首版仅本人、仅本人配额，避免变成代申请通道。
2. **申请的是什么**：`extraData.quota` 现在是“新的绝对总配额”（执行侧直接覆盖），不是“增加多少”。建议首版明确为“新总配额”，UI 用 GB 输入、后端存字节；若产品想“加 10GB”，执行侧必须改成 `当前配额 + 增量`，否则会误解。
3. **审批人是谁**：旧 flow 是系统管理员，若申请人有直属领导则优先直属领导；新版配置流没有 storage。建议首版固定“系统管理员/行政”审批，避免直属领导不掌握存储成本。
4. **上限与边界**：至少定“最小配额、最大配额、步长、是否允许降配、是否允许低于已用”。当前 `updateStorageQuota` 对负数/0/超大值全部接受；若选 A 必须在服务端校验。
5. **在途唯一性**：同一申请人是否允许同时有多张 storage 单？建议禁止，审批完成/驳回后再发起。
6. **审计**：审批日志之外，必须记录 `userId/oldQuota/newQuota/approvalId/operator`，否则无法对账。
7. **与默认配额的关系**：`user.default.storage` 只影响新建用户；storage 审批只改个人绝对值，不反向改默认值。需在文档写清。
8. **PC+MP UI**：文件页“个人存储空间”卡片加“申请扩容”；审批列表保留 storage；审批详情展示申请配额/理由；小程序是否支持发起需明确（可首版仅 PC 发起、双端审批）。
9. **旧 flow 处置**：清理/停用 `biz_approval_flow` id=4，改用统一配置流，避免“有领导走领导、没领导走管理员”的随机审批人；若只有一名管理员且本人申请，自审自批闸门会卡单，需配置至少两名审批人或固定行政审批。

### 2.4 推荐

**默认推荐 B：移除。**

理由不是“功能不重要”，而是当前证据不支持投入：

- 快照内 **0 张 storage 单据**，说明上线至今没有真实使用；
- 没有产品入口，文档却承诺了，属于“承诺大于实现”；
- 后端还有一条未校验的隐性 API 路径，保留 C 或放任不管都比移除更危险；
- 若业务确实有扩容诉求，应该先定 §2.3 的制度，再立项做 A，而不是先补 UI。

**只有满足以下任一条件才选 A**：

- 业务明确反馈“10GB 不够用，且希望员工自助申请”；
- 管理员目前已经在用改库方式处理扩容，且频次/合规压力足以支撑产品化。

否则选 B；C 只适合“已确定下一迭代做 A、当前先止血”的过渡，且过渡期也必须加类型白名单。

### 3.5 推荐

**推荐 A1 + D3。**

理由：

1. 这 31 行不是测试垃圾：有明确负责人、办事处、建档时间，且全部有 pending 的 `invoice_never` 提醒，说明系统正在把它们当真实客户催开票；把它们从“保护中”剔除（B）会让 289 掉到 258，需要改 PC+MP 多处口径，成本反而高于回填。
2. A1 只改 31 行数据，工作台、统计页、小程序、列表筛选的现有数字/文案全部保持一致；到期任务从“永远跳过”变为“2027 年正常处理”，从根上消除“统计算保护、任务不管”的分叉。
3. A1 的风险是“用建档日冒充注册日”。建议在迁移说明和产品文案中明确：**本次回填的是“保护期起算基准”，不是工商注册日；`register_date` 仅作为系统内起算日，后续可由总监/行政按真实日期修正。** 如果业务能提供真实日期，改用 A2；如果业务明确认为这 31 行不应受 360 天保护，则选 B 并接受指标下降。
4. B 是 A1 不可行时的退路，不是首选；C 把“无日期”合法化为“永久保护”，不建议；E 不解决任何问题。

**A1 的具体回填结果（按当前配置 360/180 计算，查询验证）：**

- 新 `expire_date` 范围：**2027-07-24 至 2027-08-19**
- 新 `adjust_date` 范围：**2027-01-25 至 2027-02-20**
- `protection_status` 保持 `active`，`status` 保持 `normal`
- `last_invoice_date` 保持 NULL（它是开票推导字段，不能伪造）
- 当前不会新增 `expiring` 提醒；最早在 2027-06-24 进入 30 天预警窗口
- 到期时会按 `office_id=4` 命中山西大区公海池；若届时池配置变更，以当时配置为准

### D3（P1）新建/导入客户是否强制保护期基准？

- **问题**：是否要求新建/导入客户必须有注册日（或保护期起算日），防止再产生 NULL？
- **选项**：
  - **服务端兜底（推荐）**：单条创建空值→今天；导入空值→导入日，并在结果中给行级提示；不阻断整批。
  - **强制必填**：空注册日直接拒绝/整行失败；数据质量最高，但历史导入表要补列，业务会感知。
  - **保持选填**：不推荐，D2 会周期性复发。
- **推荐**：**服务端兜底 + 导入提示**。PC 新增已默认今天，后端/导入补同口径即可；不要求 `last_invoice_date`，它是开票推导字段。
- **影响面**：`CustomerService.create`、`CustomerImportListener`、导入模板说明、客户新增页提示；只影响未来数据，不影响 31 行。
- **若选推荐的实施清单**：见 §3.7。
- **可逆性/风险**：高可逆；若未来要求真实注册日，可把兜底改为必填，但已写入的“今天/导入日”需业务确认是否需要回改。

### D4（P3，可不阻塞发布）产品下拉过滤为空是否回退全量？

## 6. 不建议现在做的项与理由

1. **不要在需求未确认时做 storage 审批全链路（A）**：0 张单据、没有 UI 入口、没有配额制度、审批人规则还不稳定；先做会得到一套“自己申请、领导闭眼批、没有上限”的流程。先把 docs 承诺收掉（B），有真实诉求再立项。
2. **不要回填 `last_invoice_date`**：它是“最近一次非作废开票”的推导字段，31 行没有任何发票；伪造开票日会同时污染保护期、报表和“从未开票”提醒。只回填 `register_date/expire_date/adjust_date`。
3. **不要为了消掉 31 行而批量改 `protection_status`**：把 31 行置 `expired`/`unset` 会让它们从列表和统计中消失，且可能触发不期望的入海/提醒口径；本问题只需要补日期，不需要改状态。
4. **不要现在启动 V2 客户状态大重构**：`V2-status-unification-design.md` 的 D7 曾倾向“unset 视同 active 以保持指标连续”；本清单的 A1 与该方向一致（通过回填让它们真正 active），不需要顺带重构 `status/protection_status` 双字段。
5. **不要现在统一全站“360 天”硬编码文案**：客户详情、导入说明、部分提醒文案仍写死 360，与 `sys_config` 可调不一致；这是独立文案/配置治理项，不是 data-5a 的阻塞项。
6. **不要立即把产品下拉改成空态**：当前 17 个大类都有产品，回退未触发；先保留防御，等字典治理有明确流程再收紧。
