## ① 结论

1. **系统状态（接口层与自动化链路层结论）**：登录鉴权、客户新建与列表/筛选/分页/详情、阶段金额/五项指标/客情字段更新、分享、公海捞取与跨人转移、延期审批、提醒、文件上传下载 ACL、激励上传与积分统计均通过，小程序 21 项契约脚本全 PASS。**限定**：①客户基本信息编辑未测、删除仅作为测试数据清理动作执行过（未作功能用例，见 ⑦-10）；②PC 系统管理/客户两维度的浏览器渲染级 UI 未实拍，以 API + 前端构建产物静态分析替代；③小程序为 DevTools 渲染器（基础库 3.17.2），未上真机。统计对账的「零差异」指 **API 与同口径 SQL 互证全等**，不代表数据本身无卫生问题——M4 乱码行、L15 冗余列恰是通过对账发现的数据问题。
2. **最要紧的问题（三条代码侧高危）**：① `customer.auto_share` 的 users 数组对元素**无类型校验/归一**，字符串 ID 一旦入库（无论何种入口）即令全体非 admin 用户的客户列表/页签计数 500，改回才恢复（`CustomerService.java:774` ClassCastException；实测样本为 4 个非 admin 账号 + admin 对照，「全体非 admin」系样本加公共代码路径外推，见 H1、⑦-1）；「运营在界面上误操作即可触发」目前只是假设——系统侧确实发生过 `[136]→["136"]` 的规则版本记录，但写入者与入口（界面/API 直调/直改库）未核实。② 小程序激励照片墙瓦片点击因 `data-record-index` 被内层 `wx:for` 遮蔽而**取错客户记录**，预览/下载不可用且存在跨客户错开文件风险（H2；本地源码已于报告定稿后修复但未回归复测，测试机部署副本仍是旧版，见 ⑤）。③ **H3 客户列表可见性口径混乱**——同一 NO001 用户：auth/info 报 `dataScope=all` 且统计模块按全量出数、客户列表却不采纳该 override 仅见 13/282（≈4.6%）；把 auto_share 四项全关后可见数反而暴涨到全库 282；缺陷还是设计未定，但反常行为已经可逆实验实证（H3）。**处置立场（有数据支撑）**：在语义确认前，「给总监再挂显式 override」不是有效止血——本次已实测 USER 11 的 `customer:view=all` override 存在而客户列表不采纳（H3 证据），问题不在缺 override 而在列表模块不消费 override；因此配置层无已验证的止血方案，只能代码修复（列表采纳 override 或 auto_share 不收窄 all）或维持现状并书面知会 NO001 用户（⑦-4）。
3. **需与代码缺陷分开处理的一条高危环境问题**：测试环境 uploads 卷历史文件大面积物理丢失——admin 口径全量遍历：激励引用集首测 713 个去重文件 711 个 404（**≈99.7%**）、复核时点 717 个引用 711 个 404（≈99.2%）；全库 `file_scope=incentive` 记录 992 条 vs 卷内 7 个物理文件（记录级缺失 >99%）；**且修订轮补查证明丢失不限于激励文件——非 incentive 53 条（public 51+private 2）中 public 48 条同样 404（94.1%）**。属测试库数据/环境治理而非代码缺陷；**其余 21 条（中 4 + 低 17，其中 L8 为待确认项非缺陷）**为中低危的口径不一致、缺校验、文案不符与样式规范偏差。

#### H1. `customer.auto_share` users 数组写入字符串 ID → 非 admin 客户列表立即 500（4 账号实测，全体系外推）

- **位置**：`PUT /api/system/configs` → `GET /api/customer/list`、`GET /api/customer/list/counts-by-filter`；根因 `CustomerService.getAutoShareOwnerIds`（`CustomerService.java:774`）。

#### H2. 小程序照片墙瓦片点击取错客户记录，预览/下载不可用（跨客户错开文件）

- **位置**：`aigicrm-miniprogram/pages/incentive/index.wxml:96,142`（及 97/101/107/108/143/147/153/154）+ `index.js:985/1001`（findRecordFile / findChildRecordFile）。
- **问题**：外层 `wx:for(records)`（wxml:70）的默认 `index` 被 `:95/:141` 内层 `wx:for(group.files)` 的默认 `index` 遮蔽，各瓦片 `data-record-index="{{index}}"` 实为**组内文件序号**而非客户卡下标；JS 用它取 `this.data.records[recordIndex]` → **取到错误客户卡的同位文件**（本例点击柳林卡组内第 1 个文件，index=0，取到第 1 张卡「邯钢唐邯潇」的文件 801；点击组内第 N 个文件会错取第 N 张卡）。后果：#4+#7 照片墙的预览/瓦片点击下载不可用，且跨客户错开文件（点 A 客户瓦片实际请求 B 客户文件 → 403「文件下载失败」）。

#### H3. 客户列表可见性口径混乱：auto_share 收窄 / override 未采纳 / 关闭共享反见全库（同一子系统三种表现）

- **位置**：`GET /api/customer/list` ↔ `GET /api/statistics/*` ↔ `GET /api/auth/info`（用户 NO001）；根因 `CustomerService.applyDataScope / applyAutoShare`（反编译 `pageList→buildListWrapper→applyDataScope+applyAutoShare`）。
- **问题**（三种已证实表现；「任务预期全量」基于 `dataScopeOverride='all'` 与 `role_perm_scope` 的 `customer:view=all` 配置推断，**该预期是否即产品设计意图未经产品确认**，见 ③-2 / ⑦-4。高危定级依据的是下列可逆实验证实的反常行为本身，不依赖设计文档）：
  1. **与任务预期全量相距甚远**：出厂配置 `{superior:true,admin:true,roles:["0"],users:[]}` 下，销售总监 NO001（override=all）客户列表仅见 **13/282（≈4.6%，复核时点快照；首测快照为 4/273≈1.5%，其间多批次漂移见 ⑤，机制不变）**（复核时点可见集 = 自有 3 + admin 名下 10）。
