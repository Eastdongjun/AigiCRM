### 1. backend:common/engine/FieldFilterAdvice.java:89 — bug

**位置**：`02-迭代源代码/aigicrm-backend/src/main/java/com/aigicrm/common/engine/FieldFilterAdvice.java` L89

**问题**：当 `Result.data` 是标量（如 `Result.success("ok")`、`Result.success(100L)`、`Result.success(true)`）或其他非 POJO（String/Number/Boolean/Date）时，`objectToMap` 里 `convertValue` 会抛异常返回 null，随后在此处抛出 500。也就是说只要命中字段规则，所有返回标量 data 的接口都会由 200 变成 500，属于可用性缺陷。建议在 `filterFields` 中对标量类型（非 Map/Collection/Result/POJO）直接原样返回，仅在真正无法脱敏的复杂对象上才 fail-closed；同时 `objectToMap` 的 `catch` 应保留原始异常信息（如 `log.warn` 或包装 cause），否则线上无法定位。

### 2. backend:common/engine/ActionGuardAspect.java:90 — bug

**位置**：`02-迭代源代码/aigicrm-backend/src/main/java/com/aigicrm/common/engine/ActionGuardAspect.java` L90

**问题**：Denial response type is incompatible with the intercepted controller method's declared return type. All `com.aigicrm.module..controller` methods declared in this project return `com.aigicrm.common.Result<T>` (e.g. `CustomerController.create(...)` returns `Result<Long>`), while the advice returns a `ResponseEntity<Map<String,Object>>` as `Object`. Spring AOP's generated proxy (CGLIB/JDK) inserts a `checkcast` to the original return type before returning to the caller, so the very first blocked `create/update/delete/...` call will throw `ClassCastException` and be handled as an unexpected 500 instead of a 403 — the guard silently fails to work as intended. The established pattern in this codebase is to throw `BusinessException`, which `GlobalExceptionHandler` already maps to HTTP 403 with a `Result` body. Replace the returned `ResponseEntity` with a thrown `BusinessException(403, ...)` (and drop the now-pointless `org.springframework.http.ResponseEntity` body building).

**建议代码**：```
        throw new com.aigicrm.common.BusinessException(403, "操作被禁止: " + action + " 权限不足");
```

### 8. backend:common/idempotency/IdempotencyService.java:60 — bug

**位置**：`02-迭代源代码/aigicrm-backend/src/main/java/com/aigicrm/common/idempotency/IdempotencyService.java` L60

**问题**：tryBegin sets a fixed 30-second TTL on the PENDING key, but there is no heartbeat/renewal mechanism. If the business operation (e.g., customerService.createWithIndicator) takes longer than 30 seconds, the PENDING key expires and a subsequent request with the same idempotency key will successfully tryBegin — leading to concurrent duplicate execution, exactly what idempotency is meant to prevent. Consider either: (1) making the PENDING TTL configurable and setting it well above the worst-case business latency; or (2) implementing a background renewal (e.g., periodic EXPIRE extension) while the operation is in progress.

**建议代码**：```
// Make TTL configurable, e.g. @Value("${aigicrm.idempotency.pending-ttl-seconds:120}") int pendingTtlSeconds
return Boolean.TRUE.equals(redis.opsForValue().setIfAbsent(scopedKey, PENDING, Duration.ofSeconds(pendingTtlSeconds)));
```
