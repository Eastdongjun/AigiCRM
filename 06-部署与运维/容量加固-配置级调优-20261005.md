## 一、改动清单（仓库内已完成）

### 1. Spring Boot 连接池与线程池（需重新构建后端镜像才生效）

| 文件 | 改动 |
|---|---|
| `02-迭代源代码/aigicrm-backend/src/main/resources/application.yml` | 新增 `spring.datasource.hikari`（maximum-pool-size=30 / minimum-idle=10 / connection-timeout=10000ms）与 `server.tomcat`（threads.max=200 / accept-count=200） |
| `02-迭代源代码/aigicrm-backend/src/main/resources/application-prod.yml` | 同值钉住（prod 档独立兜底，不随基础档漂移） |

依据：Hikari 池 30 对齐 Tomcat 200 工作线程按 ~15% 同时触库的估算，并匹配 MySQL `max_connections=300`；取池超时由默认 30s 收紧到 10s 快速失败；Tomcat 值与当前默认一致，目的是**显式钉住防升级漂移**。

### 2. nginx `/api/` 反代加固（仓库模板与服务器副本两份同构）

| 文件 | 改动 |
|---|---|
| `02-迭代源代码/nginx/nginx-ssl.conf`（模板，envsubst `${BACKEND_HOST}`） | 新增 `upstream backend_pool`（keepalive 32）；`/api/` 改走 upstream 并补 `proxy_http_version 1.1` + `proxy_set_header Connection ""`（长连接三件套）；显式 `proxy_connect_timeout 10s` / `proxy_send_timeout 60s` / `proxy_read_timeout 60s`；新增 `limit_req_zone $binary_remote_addr zone=api_limit:10m rate=30r/s`（http 上下文，conf.d 顶层合法）与 `/api/` 内 `limit_req zone=api_limit burst=60 nodelay` |
| `08-备份索引/09-生产环境备份/deploy/nginx-ssl.conf`（服务器副本，目标 `ycmn-backend:8080`） | 同构改动，仅 upstream 目标主机不同 |

定位说明：限流是**先宽后紧的兜底**——30r/s + burst 60 远超正常业务峰值（正常页面一次加载 20-40 个请求），仅拦截单一异常客户端打满 Tomcat 200 线程的场景，正常用户无感；后续按实测流量逐步收紧。

### 3. MySQL 参数（需 recreate mysql 容器才生效）

| 文件 | 改动 |
|---|---|
| `02-迭代源代码/docker-compose.prod.yml` | mysql `command` 追加：`--max-connections=300` `--innodb-buffer-pool-size=536870912`（512M）`--slow-query-log=1` `--long-query-time=2` `--slow-query-log-file=/var/lib/mysql/slow.log` |

说明：buffer_pool 取 512M 兜底——**生产宿主机总内存暂无证据**（`08-备份索引/09-生产环境备份/metadata/remote-inventory.txt` 只有磁盘/容器清单，无 free/meminfo 输出；06-部署与运维目录亦无主机规格记录），按本批任务规则不得盲调 1G。拿到内存证据后：≥6G 可上调至 1G，4-6G 维持 512M。慢查询日志落在宿主机 `/data/database/mysql-data/slow.log`（bind mount）。

### 4. JVM 堆（⚠️ 本批跳过，未改动）

`08-备份索引/09-生产环境备份/deploy/Dockerfile-run:9` 的 `-Xmx512m` **保持原样**：调到 1536m/1024m 的前提是宿主机内存 ≥6G / 4-6G，而全仓库（remote-inventory.txt、06-部署与运维、docs/ops 运维手册）均无内存证据，按"无证据不盲调"规则跳过。`02-迭代源代码/aigicrm-backend/Dockerfile` 的 ENTRYPOINT（`java -jar`，无 -Xmx 参数）也因此未动，保持两处不引入新漂移。

**取证方法**（下次运维巡检时补录）：`ssh root@39.99.35.218 free -m`，按上表阈值回填 Dockerfile-run 并同步仓库 Dockerfile。

## 三、生产生效步骤清单（按依赖顺序）

> 服务器：`root@39.99.35.218`，部署目录 `/data/ycmn`（compose 内容器名 ycmn-*，见 config-backup 备份副本）。建议低峰执行。

1. **同步 MySQL 参数**（会 recreate 容器，约 10-30s 数据库中断，放最前）：
   - 编辑 `/data/ycmn/docker-compose.yml` 的 mysql `command:`，按本仓库 `docker-compose.prod.yml` 同值追加 5 个参数；
   - `cd /data/ycmn && docker compose up -d mysql`（command 变化会自动 recreate；数据在 `/data/database/mysql-data` bind mount，不丢）；
   - 验证：`docker exec ycmn-mysql mysql -uroot -p$DB_PASSWORD -e "SHOW VARIABLES WHERE Variable_name IN ('max_connections','innodb_buffer_pool_size','slow_query_log','long_query_time')"`，应见 300 / 536870912 / ON / 2.000。
2. **同步 nginx 配置并热加载**（不中断）：
   - 将改后的服务器副本 `nginx-ssl.conf` 同步到两处：`/root/ycmn/nginx-ssl.conf`（**运行中容器实际挂载点**，见 remote-inventory MOUNTS）与 `/data/ycmn/nginx-ssl.conf`（compose 引用路径）；
   - `docker exec ycmn-frontend nginx -t` 通过后 `docker exec ycmn-frontend nginx -s reload`；
   - 验证：`curl -s -o /dev/null -w '%{http_code}\n' https://www.aigicrm.com/api/auth/login`（预期 4xx 业务码而非 502/504）；连续快速请求一批确认无限流误伤（应全 200/4xx 而非 503）。
3. **后端重新构建镜像**（hikari/tomcat 配置打在 jar 内，必须重建）：
   - 本地 `mvn package` 出新 jar → 按 `DEPLOY-STANDARD.md` 流程替换 `/data/ycmn` 的 jar → 以 Dockerfile-run 重建 `ycmn-backend` 镜像（**注意 ENTRYPOINT 是 exec 形式，-Xmx 只能写死在 Dockerfile，JAVA_OPTS 环境变量不生效**）→ 滚动重启 ycmn-backend；
   - 验证：启动日志 HikariPool 池大小 30；`docker exec ycmn-backend java -XX:+PrintFlagsFinal -version 2>/dev/null | grep MaxHeapSize` 仍为 512m（本批未调）。
4. **回滚预案**：三步各自独立可回滚——mysql 恢复原 command 再 up -d；nginx 换回 `nginx-ssl.conf.bak-*` 并 reload；后端用旧镜像 tag 重启。
