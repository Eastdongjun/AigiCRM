## P0-03 激励阅读统计/排行榜跨集团聚合

**诊断声明要点**：`readStats/readRanking` 只做权限码校验，底层聚合 SQL 从所有 `sys_user` 与全部当月 `biz_incentive_record` 统计；JdbcTemplate 原生 SQL 绕开 tenant interceptor，SQL 自身无集团条件。

**源码实际定位**：
- `IncentiveController.java`
  - `readStats` 167-171 行：`@PreAuthorize("hasAuthority('incentive:read-stats')")`
  - `readRanking` 180-184 行：`@PreAuthorize("hasAuthority('incentive:read-ranking:view')")`
  - 两个方法均仅做权限码校验，无任何集团/租户参数传递。
- `IncentiveService.java`
  - `monthlyReadAggregate(String month)` 1064-1077 行，使用 `jdbc.queryForList(...)`（原生 JdbcTemplate，不经 MyBatis-Plus TenantLineInnerInterceptor）：
    ```sql
    SELECT u.id AS userId, u.real_name AS realName, d.dept_name AS deptName,
    COUNT(DISTINCT r.id) AS publishedCount, COUNT(DISTINCT br.record_id) AS readCount,
    COUNT(DISTINCT r.id)-COUNT(DISTINCT br.record_id) AS unreadCount
    FROM sys_user u
    LEFT JOIN sys_dept d ON d.id = u.dept_id
    LEFT JOIN biz_incentive_record r ON r.created_at LIKE CONCAT(?, '%')
    LEFT JOIN biz_incentive_read br ON br.user_id=u.id AND br.record_id=r.id
    ```

**核对结果**：逐字一致。Controller 仅做权限码注解；Service SQL 从全量 `sys_user`（`u.deleted=0`）JOIN 全量当月 `biz_incentive_record`，无任何集团条件。

**结论：属实**

**备注**：`biz_incentive_record` 虽然在租户拦截表白名单内，但 `monthlyReadAggregate` 用 `jdbc.queryForList` 原生执行，租户插件不会改写 SQL，因此集团隔离完全失效。

## P1-07 JWT 黑名单权威库查询异常时 fail-open

**诊断声明要点**：注释声明"DB 为权威判定"，但 DB 查询抛异常后返回 false（即未拉黑）。

**源码实际定位**：
- `JwtTokenProvider.java` 115-137 行：
  ```java
  /** jti 是否已被拉黑...
   *  【2026-08-14 安全 P0】DB 为权威判定：Redis 命中直接 true；miss/故障一律回查 DB 黑名单表——
   *  消除"Redis 重启/淘汰后 DB 黑名单行被忽略、已撤销 token 复活"的 fail-open 窗口 */
  public boolean isBlacklisted(String jti) {
      if (jti == null) return false;
      try { ... Redis 查询 ... } catch (Exception e) { log.warn(...); }
      try {
          Integer n = jdbc.queryForObject(
                  "SELECT COUNT(*) FROM sys_token_blacklist WHERE jti=? AND expires_at>NOW()",
                  Integer.class, jti);
          return n != null && n > 0;
      } catch (Exception dbEx) {
          log.error("isBlacklisted DB 查询失败(撤销链路不可用): {}", dbEx.getMessage());
          return false;
      }
  }
  ```

**核对结果**：逐字一致。方法注释声称"DB 为权威判定"，但 catch 块（133-136 行）在 DB 查询异常时仅记录 error 日志并 `return false`，即判定 token 未被拉黑——已注销/被盗 token 在 DB 故障期间仍可通过鉴权。

**结论：属实**

**备注**：Redis 故障时回退 DB 的设计意图正确，但 DB 故障时未选择 fail-closed（抛异常拒绝请求），而是 fail-open 返回 false。这与注释中"DB 为权威判定"的承诺存在矛盾。

  ```java
      SecurityUser user = req.getUser();
      List<String> configured = configuredScopeCodes(req);

      if (user.getDataScopes() != null && user.getDataScopes().size() > 1) {
  ```

**备注**：注释明确写"降级为空(范围走 dataScope 回退, 不阻断登录)"，说明这是有意设计的可用性优先策略。但安全语义上确实是 fail-open 到更宽范围。
