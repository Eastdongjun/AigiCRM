## 任务 3：具名角色对抗审查

### 角色 A：安全工程师（Thompson 视角——信任边界与攻击链）

**A-1（置信度：高）——诊断自承"静态、未活体"，所有 P0 越权结论的可利用性仍是未证实假设，且修复建议引入了反向风险。**
报告第 4 行明确"未连接生产数据库，未进行真实多集团活体攻击测试"。P0-01/03/09 证明的是"代码路径缺少过滤条件"，但**能否真的跨租户读到数据**取决于：那些表在生产是否真的有 `tenant_id` 列、MyBatis-Plus 租户拦截器在 prod 是否真的开启（G-02 说开关三套相反默认，恰恰说明没人知道 prod 实际是哪套）。反过来，修复建议"如果旧接口无调用方就删除"——没有任何流量分析佐证无调用方，直接删可能在生产打爆某个隐藏报表。**结论：诊断的事实是"代码缺陷"，不是"已被利用"；修复动作需要的流量证据它没给。**

**A-2（置信度：高）——它抓到了黑名单 fail-open（P1-07），但漏了孪生分支：改密撤销也 fail-open。**
`JwtTokenProvider.isInvalidatedByPasswordChange()`（约 212-216 行）在任何异常时 `return false`，注释原话："Redis 故障降级为不失效，**与黑名单降级一致**"。也就是说：攻击者触发一次 Redis/DB 抖动后，①已注销 token 不失效（P1-07 已抓），②用户改密后旧 token 同样不失效（**未被 17 条收录**）。诊断按"逐条 grep 到的点"列问题，没有做"同款 fail-open 模式全库枚举"——代码注释自己都把两处标成同款了，诊断却只修一处。**攻击链：Redis 瞬时故障 → 改密/注销双失效同时失守 → 被窃 token 全程存活。**

**A-3（置信度：中）——多集团威胁模型把"集团"当唯一信任边界，忽略了 F12 自己暴露的混淆 deputy。**
F12 指出 `BizCustomer` 同时存在客户 groupName、旧 groupId/法人 ID、销售组织字段。这意味着"groupId"在系统里同时是租户边界和业务客户关系键。一个合法属于集团 A 的用户，可能在"客户所属集团 B"的记录上合法操作而不被拦截——因为代码把同一个 `groupId` 解释成了两种东西。诊断把 F12 归为"产品命名混淆/数据字典"问题，没把它当**第二信任边界缺陷**处理。

**A-4（置信度：中）——账号枚举修复只看"响应中性"，没看限流桶是否被短信轰炸反向利用。**
P1-06 要求外部响应统一；源码已有 IP 限流（AuthService:45）。但诊断没问：`lookup`、`send-code`、`reset` 三个匿名端点是否共用一个限流桶？若 send-code 独立计数，攻击者可以用"中性响应 + 独立发码限流"批量给真实手机号发短信——枚举变成了短信轰炸放大器。

### 角色 B：后端工程师（Torvalds 视角——消除特例）

**B-1（置信度：高）——P0-01/03、P1-05/09 不是四个 bug，是同一个特例："JdbcTemplate 绕过租户拦截器"。逐条打补丁必然漏。**
全库 12 个文件、19 处 JdbcTemplate 引用，诊断深审只到 CustomerService/IncentiveService/RolePermScopeService 等约 3 处；G-01 自己把"全量 JdbcTemplate 静态审计"写成待办。按报告 Top10 修复顺序去打，团队会给这 4 处加 WHERE 子句，然后在第 13 个调用点再泄露一次。**根因修复只有一个：在架构层禁用业务 Service 对租户表直用 JdbcTemplate（或强制走带 scope 参数的 helper），并把它做成编译期/门禁期约束——而不是靠人记得每条 SQL 加条件。** 诊断把症状排成 1~10 名，掩盖了它们是同一棵树上的枝。

**B-2（置信度：高）——fail-open 是一个模式散落在 ≥4 个位置：P0-02、P1-07、P1-08，加上 A-2 发现的改密分支。**
报告建议每处各自"fail-closed"。这会产生 4 套不一致的失败语义（有的拒 token、有的拒业务、有的回 none/self）。正确做法是一个授权策略点："授权元数据不可用 → 默认 deny"，所有调用点共用。诊断没有命名这个模式，等于让团队手工复制粘贴正确行为——下次新写一个查询又会回到默认放行。

**B-3（置信度：中）——P0-04 的修复建议有隐藏前提没说清：`biz_incentive_read` 表自己就没有 tenant_id 列（P0-03 自己承认了）。**
所以"加当前集团条件"在这张表上根本做不到，必须通过 record→user→group 的 JOIN 收口，这是一次 schema/查询重写，不是"写入前加一个 visibility predicate 校验"那么轻。报告两处措辞轻描淡写，会导致开发低估工作量并临时再加一个特例（比如在应用层硬过滤）。

**B-4（置信度：中）——D-01~D-05 不是五个交付问题，是一个："没有可复现构建流水线"。**
SHA256SUMS 自校验错、缺文件、无 lockfile、无 mvnw、IP 未脱敏——根因是交付物不是从同一条干净 CI 流水线产出的。五条并列 P 级会让团队打五个补丁（修路径、补 lockfile、加 wrapper……）而不去建流水线。同理 G-02"三套默认"本质是"租户开关不该是运行期可配项"——单租户部署产品的这个 flag 本身就是个不该存在的特例。

### 角色 C：产品负责人（Jobs / Cagan 视角——用户体验与业务价值）

**C-1（置信度：高）——优先级排序被安全视角主导，用户可感知的 P1 业务事故（F04 演示数据回退、F05 部分保存）被排在 SQL 聚合泄露之后，这个排序对"先让用户敢用"是错的。**
一个一线销售在真实生产点"提交客户"，后端接口 500，前端 fallback 成张三/李四和演示组织——这件事一旦发生，是**写入真实库的假数据 + 客户对系统的信任当场归零**，传播速度远高于"老板看排行榜多了几行别集团数据"（后者没人知道自己看到了错的）。按 Cagan 的"用户可发现性 × 修复成本"，F04 应该和 P0-01 同批。报告把 F04 放 P1"进入真实录单前必须修复"，措辞对了，但 Top10 风险榜里没有它。

**C-2（置信度：高）——16 个 F 主题里至少有 3 个根本不是"缺陷"，而是"尚未决策的产品问题"，混在同一修复清单里会稀释安全修复队列。**
F10（跟进≠任务）是"没建待办模块"，F11（搜索不好用）是"用户任务没满足"，F13（指标口径）是"业务制度没定"。报告第 12 节自己都写了"产品负责人应冻结的决策"，说明它知道这些不是代码 bug；但 PR-01~PR-24 任务表又把它们和 P0 安全项并列。**后果：排期会上安全补丁被"产品待决策项"稀释，真正的越权修复排队等待业务确认。** 应拆成两列：①安全/完整性必须修；②产品决策待裁决（不写代码，先开会）。

**C-3（置信度：中）——诊断没有做"用户错误链式后果"分析。**
F04（假身份写库）+ F05（部分成功、界面报错）+ F07（直接删除无业务处置）三者会同时发生在同一次失败录入里：销售网络抖动 → fallback 演示组织 → 客户建了一半 → 他以为失败删掉重录 → 连带删掉了已有票款。17+16 条全部是单点分析，没有一条把"一个手抖的销售在弱网下能造成多大业务破坏"串起来。

**C-4（置信度：中）——所有 F 主题的 P0/P1 定级零用户依据。**
报告自己第 7 行承认"没有用户访谈，岗位痛点是工作任务推演"。在 0 真实用户接触的情况下把 F08（保护期 360 vs 365）定成 P1、把 F10 定成 P1/P2，本质是猜。Discovery 视角：这些定级应该随第一批真实客户的使用证据滚动调整，而不是写死进修复顺序。

## 综合裁决

**结论：诊断结论方向正确、工程素养扎实，但不能直接作为修复 backlog 原样执行。**

可以直接采纳的部分：
- P0-01~P0-04、P1-05~P1-09 的越权/fail-open 定性，以及"上线阻断批 = P0 系 + 租户 fail-closed"的大方向，成立。
- G-01 的"授权语义门禁 + 故障注入测试"建议正确。
- 两份报告自己都明确说了"静态门禁不能替代真实联调"——这个自我克制是可信的。

直接执行前必须补的五件事：
1. **把 fail-open 作为模式全库枚举**，而不是逐条修：P0-02、P1-07、P1-08 + 本次新发现的 `isInvalidatedByPasswordChange` 孪生分支（JwtTokenProvider 约 212-216 行）应合并为一个"授权/失效元数据不可用即 DENY"策略点。
2. **把 JdbcTemplate 直连作为架构级收口**：完成 G-01 自己列的待办——12 个文件、19 处引用全部过一遍（含是否有用户输入拼 SQL 的 A03 残余面），在门禁层禁止业务 Service 对租户表裸用 JdbcTemplate。
3. **补 STRIDE 两个盲区**：R（审计日志 append-only、管理员自身操作被审计、越权事件事后可追溯）与 D（全表聚合查询上限、导入/上传大小与类型限制、租户级资源配额）。
4. **补 A09 盲区**：安全事件（登录失败、越权拒绝、权限/租户变更）的结构化日志与告警阈值；P1-06 改中性响应后内部日志必须足以检测枚举。
5. **把清单拆成两列**：安全/完整性必须修（P0 系 + fail-open 模式 + R/D 盲区）vs 产品待决策项（F08/F10/F11/F13 等先开会定制度再写码）；并把 F04 演示数据回提升级为与 P0-01 同批——它是用户侧最快炸、且会污染真实库的一项。

置信度声明：本报告对 A02/A03/A10 的盲区结论基于只读 grep 快扫（未逐文件精读），其中"12 个 JdbcTemplate 文件未全审"和"改密 fail-open 孪生分支"为**高置信**；"JWT alg 未固定""上传无类型限制"为**中置信**，修复前应精读对应文件确认。
