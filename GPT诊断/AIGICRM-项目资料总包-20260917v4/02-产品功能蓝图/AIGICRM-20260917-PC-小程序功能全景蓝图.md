## 1. 产品定位与系统边界

AIGICRM 是以“客户全生命周期”为核心，连接客户、销售、四项激励、文件、提醒、公海、审批、统计、积分和组织权限体系的企业级 CRM。

系统包含两个业务客户端：

1. **PC 管理端**：完整管理后台，承担高密度数据处理、批量操作、配置、权限、组织、系统治理、复杂统计和管理动作。
2. **微信小程序**：一线移动工作端，承担随时查询、客户现场维护、文件查看、激励录入、审批、公海捞取、提醒处理、统计查看等轻量业务。

二者不是两个独立系统，而是**同一个业务系统的两种终端形态**：

```text
PC Vue3 管理端 ─┐
                ├── Spring Boot API ── MySQL / Redis / 文件存储
微信小程序 ─────┘

统一：账号 / 用户 / 集团 / 组织 / 角色 / 岗位 / 权限 / 数据范围 / 业务数据 / 审计日志
差异：页面形态 / 操作密度 / 是否开放高风险动作
```

### 1.1 必须坚持的产品原则

- 一个账号体系：PC 和小程序使用同一个 `sys_user`。
- 一个权限源：权限最终来自后端，不允许 PC、小程序各维护一套业务权限。
- 一个数据源：客户、激励、文件、公海、审批等必须访问同一套业务表。
- 一个集团上下文：集团切换后，两端数据范围必须一致。
- 一个审计链：关键写操作必须能够追溯到用户、时间、对象、动作、结果、来源终端。
- 前端隐藏按钮只是体验控制，**后端接口和 Service 层才是最终安全边界**。
- 高风险管理动作优先保留在 PC；小程序只开放明确接受并经过权限与行级校验的动作。

# 2. 全系统业务域地图

| 一级业务域 | 核心能力 | 主要对象 |
|---|---|---|
| 认证与账户 | 登录、登出、找回密码、修改密码、集团切换、用户信息 | 用户、Token、集团 |
| 工作台 | 我的客户、提醒、审批、业务指标、快捷入口、团队动态 | 聚合指标 |
| 客户管理 | 客户主数据、联系人、跟进、财务、指标、共享、保护、释放 | 客户、联系人、日志、发票、回款 |
| 文件中心 | 文件夹、上传、预览、下载、替换、分享、ACL | 文件、文件夹、ACL、分享 |
| 四项激励 | 分类、记录、附件、分值、统计、查询、阅读状态、排行榜 | 激励分类、激励记录、阅读记录 |
| 提醒管理 | 到期提醒、待办、处理 | 提醒 |
| 公海管理 | 公海池、可见范围、导入、捞取、编辑、删除、捞取记录 | 公海池、公海配置 |
| 审批中心 | 申请、待办、审批、驳回、流程节点、审批配置 | 审批单、审批节点、流程 |
| 统计分析 | 日/周/月、趋势、排行、团队动态、客户指标 | 聚合视图 |
| 积分管理 | 积分项、积分录入、排行、统计、导出 | 积分项、积分记录、参与人 |
| 核心客户六项指标 | 指标录入、评分、核心客户识别、排行 | 客户指标 |
| 系统管理 | 集团、组织、人员、角色、岗位、规则、配置、日志、权限范围 | RBAC/ABAC 基础对象 |

### 3.3.3 客户详情

【现有】建议按以下业务卡片理解：

1. **客户基础信息**
   - 客户名称、行业、类型、区域、归属等。
2. **客户负责人/归属**
   - 当前负责人、组织、集团。
3. **跟进日志**
   - 查看跟进历史。
   - 新增跟进记录。
4. **联系人**
   - 联系人列表。
   - 新增、编辑、删除联系人。
   - 联系人敏感信息额外受 `contact:view` 控制。
5. **财务信息**
   - 发票列表、发票汇总。
   - 回款列表、回款汇总。
   - 新增/删除财务记录。
   - 财务区域额外受 `finance:view` 控制。
6. **客户关系评分**
   - 维护客户关系分值。
7. **六项指标**
   - 查询与维护客户六项指标。
8. **四项激励关联**
   - 查看该客户的激励记录和积分。
9. **客户分享**
   - 添加共享用户。
   - 取消共享。
10. **客户释放**
   - 填写原因。
   - 进入公海业务链路。

### 3.3.4 客户权限码

- `customer:view`
- `customer:add`
- `customer:edit`
- `customer:delete`
- `customer:import`
- `customer:export`
- `customer:share`（当前部分逻辑兼容历史语义）
- `customer:date:edit`
- `contact:view`
- `finance:view`

### 3.3.5 客户数据范围

客户是否可见/可操作，应综合：

- 当前集团。
- 当前负责人/Owner。
- 首负责人。
- 用户本人。
- 团队上下级。
- 部门/组织子树。
- 办事处。
- 大区。
- 自定义组织集合。
- 客户共享。
- 公海状态。
- 单操作的数据范围（view/edit/delete/share 可不同）。

### 【建议补齐】客户产品化能力

以下属于目标产品建议，不等于当前已实现：

- 客户唯一编码规则。
- 客户主数据合并/查重/去重。
- 客户转移、批量转移。
- 客户负责人变更历史。
- 客户黑名单/无效客户。
- 客户标签体系。
- 客户分级（A/B/C 或战略/重点/普通）。
- 商机、报价、合同、订单等后续销售链条（当前源码并未形成完整模块）。
- 批量编辑。
- 客户归档/恢复。
- 客户敏感字段脱敏。

## 4.7 权限范围管理

`role_perm_scope` 用于定义：

```text
受权对象类型 ROLE / POSITION / USER
+ 受权对象
+ module
+ action
+ scope_level
+ anchor
```

因此同一个用户可以：

- customer:view = dept
- customer:edit = self
- customer:delete = self
- customer:export = custom

这比“一个角色只有一个 dataScope”更符合真实企业权限。

# 6. PC 与小程序的关系

## 6.1 六个“必须一致”

| 维度 | PC | 小程序 | 统一要求 |
|---|---|---|---|
| 身份 | JWT 用户 | JWT 用户 | 同一个 `sys_user` |
| 集团 | 当前集团 | 当前集团 | 切集团后均重新加载权限和数据 |
| 功能权限 | 菜单/按钮 | 入口/按钮 | 同一权限码 |
| 数据范围 | Service/SQL | Service/SQL | 后端统一计算 |
| 业务数据 | 同一数据库 | 同一数据库 | 不允许移动端本地业务副本 |
| 审计 | PC 操作日志 | 小程序操作日志 | 同一审计体系，标识终端来源 |

## 6.2 两端功能分工

### PC 更适合
- 系统管理。
- 权限配置。
- 集团/组织配置。
- 角色/岗位配置。
- 导入导出。
- 批量操作。
- ACL 写。
- 公海配置。
- 审批配置。
- 激励分类配置。
- 积分项和积分录入。
- 复杂统计和后台治理。

### 小程序更适合
- 快速查询。
- 现场客户维护。
- 客户跟进。
- 联系人维护。
- 轻量财务录入。
- 文件查看/上传/分享。
- 激励上传/阅读。
- 审批。
- 公海捞取。
- 提醒处理。
- 排行和统计查看。

## 6.3 同步机制

业务数据：
- PC 改客户 → 小程序刷新后看到同一结果。
- 小程序写跟进 → PC 客户详情应立即可查询。
- 小程序审批 → PC 审批状态和对应业务状态应同步。
- 激励阅读状态由 `biz_incentive_read` 统一保存，两端同账号一致。

权限数据：
- PC 修改角色/权限。
- 后端清理权限缓存并递增 `permVersion`。
- 小程序/PC 下一次 `/api/auth/info` 或权限刷新后收敛到新权限。

# 10. 权限体系——不能只做 RBAC

完整权限至少分 9 层：

1. **身份权限**：是否是有效用户、当前集团是否合法。
2. **菜单权限**：是否看到某个模块。
3. **页面权限**：是否可以直接进入某个页面。
4. **按钮权限**：新增、编辑、删除、导入、导出、审批等。
5. **API 权限**：后端 `@PreAuthorize`。
6. **字段权限**：联系人、财务等敏感字段。
7. **数据范围权限**：能看哪些记录。
8. **单条对象权限**：这一个客户/文件/公海记录是否可以编辑、删除、分享、捞取。
9. **审计权限**：关键动作必须留痕。

### 典型例子

某销售经理可以配置成：

```text
customer:view   = team
customer:edit   = self
customer:delete = self
customer:export = dept
file:view       = dept
approval:view   = team
statistics:view = dept
```

因此“看得到”和“改得了”不能使用同一个范围。

# 11. 数据范围模型

## 11.1 当前范围码

| Code | 含义 |
|---|---|
| `all` | 当前集团内全部数据 |
| `custom` | 指定组织/用户范围 |
| `region` | 大区范围 |
| `office` | 办事处范围 |
| `dept` | 部门范围 |
| `dept_and_children` | 兼容历史部门子树 |
| `org` | 指定组织节点 |
| `org_and_children` | 组织及下级 |
| `team` | 管理者下属链 |
| `self` | 本人数据 |

Scope Anchor：
- `OWNER`：按负责人/上传人/申请人等计算。
- `ORG`：按组织、部门、办事处等计算。

## 11.2 现有优先级

1. USER 级 `role_perm_scope`。
2. POSITION 级 `role_perm_scope`。
3. ROLE 级 `role_perm_scope`。
4. 用户 `data_scope_override` / 角色默认 data scope。
5. 无配置时：view 使用默认范围；写动作倾向 `self`。

## 11.3 安全基线要求

基于本轮审计，建议把安全顺序明确成：

```text
先做集团隔离
→ 再做 module/action scope
→ 再做组织/Owner 过滤
→ 再做共享/ACL/专项授权
→ 最后做对象级 canEdit/canDelete/canShare
```

**没有合法集团上下文时必须 fail-closed，不应该自动落入主集团。**

# 14. 核心端到端业务流程

## 14.1 用户开通与权限配置流程

```text

→ 创建组织/部门
→ 创建角色
→ 角色绑定菜单/权限
→ 创建岗位
→ 配置岗位规则/数据范围
→ 配置 ROLE/POSITION/USER module-action scope
→ 创建用户
→ 绑定集团/组织/角色/岗位
→ 用户登录
→ /api/auth/info 返回权限
→ PC/小程序按同一权限工作
```

## 14.2 客户生命周期

```text
新增/导入客户
→ 查重
→ 指定集团/组织/负责人
→ 进入保护期
→ 跟进日志 / 联系人 / 财务 / 六项指标 / 激励持续沉淀
→ 到期提醒
→ 继续维护 或 释放/超期
→ 进入公海
→ 公海可见范围判断
→ 发起捞取
→ 审批

```

```text
客户详情
→ 新增跟进日志
→ 保存
→ 时间线更新
→ 工作台/团队动态可聚合
→ 后续提醒/保护判断继续
```

【建议补齐】跟进类型、下次跟进时间、跟进结果、附件、协同人、自动提醒。

## 14.4 客户财务流程

```text

→ 查看客户财务
```

## 14.5 客户释放到公海

```text
客户正常状态
→ 用户点击释放
→ 填写释放原因
→ 校验 customer 权限和对象范围
→ 写入公海池/状态
→ 普通客户列表变化
→ 公海可见用户看到
```

如果业务配置要求审批，则应：申请 → 审批 → 最终进入公海。

---

## 14.6 公海捞取流程

```text

→ 后端返回 canClaim
→ 点击捞取

→ 审批人通过/驳回
→ 通过：客户 Owner 变更 + 公海记录完成

```

# 19. 异常、边界与防错设计

## 19.1 权限边界
- 无功能权限：菜单/按钮隐藏，API 403。
- 有菜单权限但无行权限：可进页面但看不到越权数据。
- 有 view 无 edit：详情可看但写操作隐藏且 API 拒绝。
- 有财务/联系人基础客户权限但无字段权限：对应敏感区域不可加载。

## 19.2 集团边界
- 用户只能切到授权集团。
- 切集团后缓存、菜单、统计、业务列表必须刷新。
- 当前集团为空或非法时应拒绝业务查询，不自动切主集团。

## 19.3 删除
所有小程序删除动作：
- 必须独立权限/服务守卫。
- 必须对象级范围。
- 必须二次确认。
- 必须审计。

## 19.4 导入
建议：
- 模板版本校验。
- 预校验。
- 错误行报告。
- 幂等/重复处理策略。
- 大批量异步任务。
- 导入审计。

## 19.5 导出
建议：
- 继承列表数据范围。
- 敏感字段再次过滤。
- 导出数量上限。
- 异步导出。
- 水印。
- 下载有效期。

## 19.6 文件
- 路径不能由客户端任意传入访问。
- 下载 token 短时有效。
- ACL 与下载设置必须后端校验。
- 老附件缺失要明确区分“元数据存在、物理文件不存在”。

# 21. 测试与验收矩阵

不能只验“功能能点”。每个模块至少做以下矩阵：

```text
角色：管理员 / 总监 / 经理 / 销售员 / 行政 / 财务 / 审计
×
岗位：总部 / 大区 / 办事处 / 部门 / 普通人员
×
范围：all / custom / region / office / dept / team / self
×
集团：A / B
×
终端：PC / 小程序
×
动作：view / create / edit / delete / share / import / export / approve
```

重点验收：
- PC 能看，小程序也应该能看同一数据（若功能已开放）。
- PC 不能看，小程序绝不能通过直接 API 看。
- A 集团不能读取 B 集团数据。
- `self` 用户不能编辑他人客户。
- `team` 只覆盖合法上下级。
- 字段级权限不能只靠前端隐藏。
- 统计数字必须与明细可见范围一致。
- 权限变更后 PC/小程序都能及时收敛。

# 24. 最终产品定义

AIGICRM 应被定义为：

> **以集团和组织权限为安全边界，以客户生命周期为主线，以 PC 管理端 + 微信小程序移动端为双入口，统一客户、跟进、联系人、财务、四项激励、文件、公海、审批、提醒、积分和统计分析的企业 CRM 平台。**

PC 与小程序共享同一用户、同一权限、同一数据范围和同一业务状态；PC 负责完整治理和高风险管理，小程序负责一线移动操作；角色决定“能做什么”，岗位和组织决定“管哪里”，用户级范围决定“个人例外”，字段权限和对象权限决定“具体能看到/能改到什么程度”。

这份蓝图后续应继续拆成以下开发交付件：

1. 《PC 页面级 PRD》
2. 《小程序页面级 PRD》
3. 《角色-岗位-权限-数据范围矩阵》
4. 《业务流程与状态机说明书》
5. 《字段级数据字典》
6. 《接口权限矩阵》
7. 《统计指标口径字典》
8. 《异常码与防错规则》
9. 《PC/小程序一致性验收矩阵》
10. 《UI 组件与交互规范》
11. 《上线初始化配置手册》
12. 《实施交付与权限开通模板》
