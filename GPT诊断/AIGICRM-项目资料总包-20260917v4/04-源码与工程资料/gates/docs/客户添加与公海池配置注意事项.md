# 客户添加 与 公海池配置 注意事项

> 面向运维/管理员。整理自生产实际排查（含"王磊磊看不到公海客户"等真实问题）。
> 最后更新：2026-07-21

---

## 零、先理解组织架构（一切的前提）

系统组织是四层树，`sys_dept.dept_type` 区分层级：

| type | 含义 | 生产示例 |
|---|---|---|
| 1 | 总部 | 艾志（南京）… |
| 2 | 大区 | 山西大区 / 内蒙古大区 / 河北大区 |
| 3 | **办事处** | 太原办销售部(4) / 内蒙办销售部(6) / 河北团队销售部(44) |
| 4 | 部门 | 太原办行政部 / 内蒙办行政部 … |

**关键：`dept_type=3`（办事处）是公海池归属的唯一锚点。** 客户属于哪个办事处，就决定它释放后进哪个公海池。大区、部门都不直接参与公海匹配。

> ⚠️ 每个大区下**必须至少有一个 type=3 办事处**，否则该大区的客户无法释放到公海（会报"未配置公海池"）。当前河北大区仅 1 个办事处，务必保留。

## 一、客户添加注意事项

### 1. 大区 + 办事处 必选且联动
- 新增客户页，"所属大区"和"所属办事处"两个下拉**联动且都必填**：先选大区，办事处只列出该大区下的（`office.parentId === regionId`）。
- **办事处（office_id）才是决定公海归属的字段**；大区（region_id，07-11 新增）只做展示/联动，**不参与公海匹配**。
- 选错办事处 → 客户以后释放会进错池，或匹配不到池而无法释放。

### 2. 第一负责人
- 新增模式下，"第一负责人"默认是当前登录人；可改。编辑模式不自动改。

### 3. 客户编号
- 前缀取**大区的 `dept_code`**（如 SX/NM/HB）。若大区 `dept_code` 为空 → 编号退回兜底前缀 "C-"。
- 新建大区时**务必在组织架构里填"大区编码"**，否则该大区新客户编号异常。

### 4. 所属单位 / 开票名称
- 列表"所属单位"列 = `unit_name`；新增页"开票名称" = `invoice_name`。两者是独立文本字段，据实填写。

### 5. 批量导入
- 导入的客户 `office_id` 取**导入人当前的 office_id**。用错账号导入 → 客户办事处全归到导入人名下的办事处，后续公海归属会错。**用目标办事处的账号导入**。

## 二、公海池配置注意事项

配置入口：公海管理 → 公海池配置（`biz_sea_config`）。

### 1. 一个公海池 = 一组"可见部门/人员" + 派生的办事处范围
配置里选的是**组织树上的部门(type=4)/人员**，保存时系统自动：
- **可见性**：谁能在公海页看到这个池 = 选中的部门/人员（`visible_dept_ids` / `visible_user_ids`）。
- **归属范围**：把选中的部门/人员**向上折算到最近的 type=3 办事处**，存进 `region_ids`（字段名叫 region，**实际存的是办事处 ID**，不是大区 ID）。

### 2. 可见性规则（决定销售能不能看到可捞取客户）
非管理员用户，看到某个池的前提是**满足其一**：
- 其 `user_id` ∈ 池的 `visible_user_ids`，**或**
- 其 `dept_id` ∈ 池的 `visible_dept_ids`。

> 管理员（data_scope=all）看得到全部池，不受此限。
> 排查"某销售看不到公海客户"时，**先查他的 user_id/dept_id 有没有落进目标池的可见范围**。

### 3. 办事处不能跨池重叠（系统强制）
- 一个办事处（type=3）**只能属于一个公海池**。保存时若发现该池派生出的办事处已被别的池占用，会直接报错拒绝（`checkOfficeOverlap`）。
- 目的：避免释放时"多池命中、取哪个不确定"。
- ⚠️ **历史遗留**：生产现有三池的 `region_ids` 曾大面积重叠（含总部/大区 id）。**要再次编辑这三池前，必须先把重叠清理干净**，否则保存会被拦。

### 4. 匹配用办事处 ID（务必对齐）
- 客户释放时：`matchSeaConfig(客户.office_id)` 拿**办事处 ID** 去逐个比对各池的 `region_ids`，命中即入该池。
- 因此**池的 `region_ids` 必须包含目标客户的 `office_id`**，否则：
  - 手动释放 → 报"该客户所属办事处未配置公海池，无法释放"；
  - 定时/导入释放 → 静默入池但 `pool_id=NULL`（见下方"坑"）。

## 三、已知陷阱（务必知道）⚠️

### 坑 1：配置改动后，已入池客户的 pool_id 不会自动回填
- `biz_sea_pool.pool_id` 是**客户入池那一刻的一次性快照**。之后你修改公海池配置的 `region_ids`，**已经在池里的记录不会重算**。
- 后果：客户入池时若没匹配到池（pool_id=NULL），哪怕你事后把配置改对了，这些老记录仍是 NULL。
- **表现**：非管理员销售**一条都看不到**（因为按 `pool_id IN (可见池)` 过滤，NULL 匹配不上）；管理员却看得到 → 极具迷惑性。
- **补救**：改完配置后，对受影响的 available 记录**手工回填 pool_id**（按 office_id → 目标池），或找开发跑回填。

### 坑 2：匹配不到池时静默写 NULL，无任何告警
- 定时任务/批量导入路径下，`matchSeaConfig` 返回 null 也照样入池，`pool_id` 存 NULL，**不报错、不记日志**。客户就此"隐身"。
- **自查**：定期跑
  ```sql
  SELECT COUNT(*) FROM biz_sea_pool WHERE pool_id IS NULL AND status='available';
  ```
  结果 >0 说明有隐身客户，需回填。

### 坑 3：配置生效有"时序"要求
- 释放动作**用的是当下的配置**。若"客户先释放、配置后修好"，中间入池的记录就是 NULL（坑 1）。
- **正确顺序**：先把大区/办事处/公海池配置齐活，再导入/释放客户。

### 坑 4：账号重复 / 测试节点污染
- `sys_user` 无 username/phone/real_name 唯一约束，容易建出重复人（生产曾有 3 个"王磊磊"）。**建号前先按手机号查重**。
- 组织架构里的测试节点（如顶层"测试"办事处 id=40）会出现在选择器里，**建客户/配池时别误选**，建议及时清理。

## 四、上线/变更前检查清单 ✅

新建大区/办事处/公海池，或批量导入客户前，逐项核对：

- [ ] 目标大区已建，且填了**大区编码 dept_code**（影响客户编号）。
- [ ] 大区下**已建 type=3 办事处**，客户能选到正确办事处。
- [ ] 公海池配置里，该办事处**已被某个池的 region_ids 覆盖**，且**不与其它池重叠**。
- [ ] 该池的"可见部门/人员"**已包含目标销售**（user_id 或 dept_id 命中）。
- [ ] 顺序：**先配好组织+公海池，再导入/释放客户**。
- [ ] 导入客户用的是**目标办事处的账号**（决定 office_id）。
- [ ] 变更配置后，跑一次 NULL 自查 SQL（坑 2），有残留就回填。

## 五、常用排查 SQL

```sql
-- 某销售(替换 real_name)能看到哪些池
SELECT id, pool_name,
       FIND_IN_SET(<user_id>, visible_user_ids)>0 AS by_user,
       FIND_IN_SET(<dept_id>, visible_dept_ids)>0 AS by_dept
FROM biz_sea_config HAVING by_user OR by_dept;

-- 各池待捞取客户数
SELECT pool_id, status, COUNT(*) FROM biz_sea_pool GROUP BY pool_id, status;

-- 隐身客户（入池但没归属池）
SELECT sp.id, c.customer_name, c.office_id
FROM biz_sea_pool sp JOIN biz_customer c ON sp.customer_id=c.id
WHERE sp.pool_id IS NULL AND sp.status='available';

-- 回填 pool_id（按 office_id → 目标池，改完先备份）
UPDATE biz_sea_pool sp JOIN biz_customer c ON sp.customer_id=c.id
SET sp.pool_id=<池id>
WHERE sp.pool_id IS NULL AND sp.status='available' AND c.office_id=<办事处id>;
```

## 附：字段速查

| 字段 | 表 | 含义 | 参与公海匹配? |
|---|---|---|---|
| `office_id` | biz_customer | 客户所属**办事处**(type=3) | ✅ 是（匹配锚点） |
| `region_id` | biz_customer | 客户所属大区(07-11 新增) | ❌ 否（仅展示/联动） |
| `region_ids` | biz_sea_config | 池覆盖的**办事处 ID** 列表（名字叫 region 但存办事处） | ✅ 是 |
| `visible_dept_ids` / `visible_user_ids` | biz_sea_config | 池的可见部门/人员 | 决定可见性 |
| `pool_id` | biz_sea_pool | 入池时快照的归属池（**不自动回填**） | 决定列表过滤 |
